# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

T-Pot is a multi-honeypot platform: ~30 honeypots plus NSM tools (Suricata, p0f) and the Elastic Stack, all run as Docker containers via docker compose. There is no application build in the usual sense — the repo is Dockerfiles, compose files, shell scripts, and an Ansible-based installer. The installed checkout lives at `~/tpotce` on the target host, and many scripts hard-code that path (`$HOME/tpotce`).

## Commands

### Building images (`docker/_builder/`)
- `docker/_builder/docker-compose.yml` is the build-only manifest listing every image (multi-arch amd64/arm64 via buildx). Its settings (`TPOT_DOCKER_REPO`, `TPOT_GHCR_REPO`, `TPOT_VERSION`, platforms) come from `docker/_builder/.env`.
- Build all: `sudo docker/_builder/builder.sh` (run from `docker/_builder`; requires root; `-n` no-cache, `-p` push to Docker Hub + GHCR). `setup_builder.sh` prepares a build host.
- Build one image: `cd docker/_builder && docker compose build <service>`, or `cd docker/<service> && docker compose build` (each service dir has its own standalone `docker-compose.yml` with `build: .`).

### Smoke tests (`docker/_tests/`)
Post-build container tests; they require the image to already exist locally and never build.
- All: `./docker/_tests/run.sh`; list: `./docker/_tests/run.sh --list`
- One: `./docker/_tests/run.sh cowrie` or directly `./docker/_tests/tests/cowrie.sh [--image ...] [--<proto>-port ...]`
- Options: `--timeout SEC`, `--bind-ip IP`, `--keep-artifacts`
- Conventions for new tests: one executable `tests/<service>.sh` per honeypot, source `lib/common.sh` (`test_*` helpers for compose, port checks, waiting on log text, cleanup), bind to loopback, prefer dynamic host ports, temp files under `/tmp`, fail with an image build hint when the image is missing. Some tests need host tools (e.g. dicompot needs DCMTK).

### On a running T-Pot host (from `docker/tpotinit/dist/bin/`)
- `hptest.sh [-B file] [--tools-only] [host]` (`tpot check honeypots`) — probes honeypots listed in `~/tpotce/docker-compose.yml` (ports from `docker compose config --format json`, the tools per distribution from `fuTOOLS_FOR`).
- `attackmap_pipeline_test.sh [--types ...] [--ips ...] [--dry-run] [-B file]` (`tpot check pipeline`) — end-to-end check: injected honeypot JSON → Logstash → Elasticsearch → map_data → Redis → map_web WebSocket. Injected events are real and not cleaned up.
- Both run from the *Checks* page in the task screen, in the look of `installer/lib/ui.sh` with `fuMARK` phases (a plain fallback inside the tpotinit image). `mytopips.sh` is `tpot attackers`.

### tpot command and its tests
- `./tpot -h` lists the sub-commands; `./tpot setup` builds the venv.
- `python3 -m unittest discover tpotctl/tests` runs the non-UI tests; the Textual UI tests are skipped there and run with the venv: `~/.local/share/tpotce/venv/bin/python -m unittest discover tpotctl/tests`.
- After changing `tpotctl/requirements.in`: `uv pip compile tpotctl/requirements.in --universal --generate-hashes --python-version 3.9 --only-binary :all: --no-header -o tpotctl/requirements.txt`, then put the header comment back.

### Lifecycle
`install.sh`, `update.sh`, `uninstall.sh`, `restore.sh`, `genuser.sh`, `deploy.sh` (sensor → hive). `install.sh` without `-s` at a terminal installs its packages (+ git, python3-venv), clones the repo to `~/tpotce`, runs `tpot setup` and hands over to the assistant `tpot install` (`tpotctl/installer.py` + `screens/install.py`), which asks everything up front and runs `install.sh -s -M` with the answers (`-P` web password file, `-B` sudo password file, `-c` customizer file; `-M` prints `@@tpot phase|tasks|images|warn` marks the assistant reads with the Ansible `TASK [` lines); without the venv or with `-n` it asks the classic questions (before the playbook). Every mode takes the playbook from the clone. `uninstall.sh -y [-k] [-B file]` (`-k`: `update.sh -y --backup-only --full` first), `tpot uninstall` asks (host name) and execs it. All of them style their output through `installer/lib/ui.sh` (gum, pinned release with sha256, plain text without a terminal or `TPOT_GUM=off`); `install.sh` carries an identical copy of that block because it runs from curl. Both `install.sh` and `update.sh` accept `-b <branch>` / `-r <repo-url>` (env `TPOT_BRANCH` / `TPOT_REPO_URL`) for testing a branch or fork; see README "Testing a Branch" for precedence rules. Runtime is controlled via `systemctl start|stop tpot` (unit in `installer/install/tpot.service`).

## Architecture

- **`tpotinit` is the orchestrator.** Every compose file starts with the `tpotinit` service (host networking, NET_ADMIN, docker socket, mounts `${TPOT_DATA_PATH}` as `/data`); all other services `depends_on` it being healthy. Its `docker/tpotinit/dist/entrypoint.sh` validates `.env` (rules in `dist/etc/env.schema.yml`, read with `yq` by `dist/bin/env_validate.sh`; all errors at once, service settings only if the service is in the compose file), creates/permissions the data folder, sets up web users, blackhole routes, iptables NFQ rules (for glutton/honeytrap), interface config for the NSM services, imports Kibana objects on fresh HIVE installs, and runs autoheal. The capture interface comes from `dist/bin/capture-if.sh` (`TPOT_CAPTURE_INTERFACE` or the route to the internet); identical copies live in `docker/{suricata,p0f,glutton}/dist/` and must be kept in sync. Host-side helper scripts ship inside this image under `dist/bin/`.
- **Editions are compose files in `compose/`.** `standard.yml`, `sensor.yml`, `mini.yml`, `llm.yml`, `tarpit.yml`, `mobile.yml`, `mac_win.yml`. The root `docker-compose.yml` is the active one and is a copy of `compose/standard.yml` — keep them in sync when editing the standard edition. `tpot_services.yml` is the service catalogue that `compose/customizer.py` (logic in `customizer_core.py`, UI-free `State` + text dialog in `customizer_tui.py`, full screen dialog in `tpotctl/screens/customizer.py`; headless/`--rebuild` need only stdlib + PyYAML, Python ≥ 3.9, the distro package comes from the installer / `update.sh` `fuCUSTOMIZER_DEPS`, else the tpot venv) uses to build a custom compose file: an edition as base plus added/removed services and host-port overrides, written into a `# customizer:` header with a sha256 of the body so `update.sh` (`fuRESTORE_CUSTOM`) can `--rebuild` it on updates unless it was hand-edited. Every catalogue service needs an `x-tpot` line (group, description, optional requires/conflicts/hidden/hive_only/linux_only/required); editions may only differ from the catalogue in ports, networks and depends_on (mac_win also network_mode, cap_add, volumes). Run `python3 -m unittest discover compose/tests` after touching any compose file. Adding/changing a service usually means touching several of these files plus `docker/_builder/docker-compose.yml` and `docker/<service>/docker-compose.yml`.
- **Configuration**: `.env` (defaults in `env.example`) feeds both compose variable substitution (`TPOT_REPO`, `TPOT_VERSION`, `TPOT_PULL_POLICY`, `TPOT_DATA_PATH`, ...) and tpotinit (`TPOT_TYPE=HIVE|SENSOR`, `TPOT_BLACKHOLE`, `TPOT_HIVE_*`, `WEB_USER`, ...). Note `.env` and `docker-compose.yml` are listed in `.gitignore` but are tracked — edits to them do show in diffs.
- **Per-service layout**: `docker/<service>/{Dockerfile, docker-compose.yml, dist/}`. Containers are generally `read_only` with tmpfs, run as uid/gid 2000, and write logs to `${TPOT_DATA_PATH}/<service>/log`. Image tags follow `version` (currently `24.04.2`).
- **Data flow**: honeypots write JSON/log files under `/data/<service>/log/` → Logstash (`docker/elk/logstash/dist/logstash.conf`) tails each file with a per-honeypot `type` and filters (date, geoip, ip_rep, hostname) → Elasticsearch `logstash-*` → Kibana. On a SENSOR, Logstash swaps in `pipelines_sensor.yml` and ships events over HTTPS (`http_output.conf`) through nginx to the hive's `http_input.conf`. A new honeypot needs a Logstash input + filter block to show up in Kibana/Attack Map.
- **Beelzebub and Galah** (`docker/beelzebub/`, `docker/galah/`) build their upstream repos at a pinned commit plus a T-Pot overlay: new Go files in `dist/tpot/` (the flat log format of the former T-Pot forks; Beelzebub also persists the SSH host key and expands `${VAR}` in service YAMLs) and one-line hooks in `dist/tpot.patch`. On an upstream bump, update the commit in the Dockerfile; a hook that no longer applies or compiles fails the build. The log format must stay as it is, ewsposter reads `beelzebub.json` / `galah.json` directly; ES-only normalization (`status_text`, Galah's `http_request.*` / `http_response.*` via `de_dot`) lives in Logstash. Both builders cross-compile on `$BUILDPLATFORM` (Go crashes under QEMU), Galah needs CGO and uses `tonistiigi/xx`.
- **p0f** (`docker/p0f/`) is the original p0f 3.09b C code with T-Pot changes: JSON log (jansson), per-packet skipping of up to two VLAN tags on Ethernet (the original only handled untagged frames), `-o -` for JSON on stdout (offline mode via the entrypoint `dist/run.sh`: no arguments = live capture with a BPF filter for the host's own SYNs by packet direction (`outbound`, live only), arguments go to p0f, own `-j` / `-o` replace the defaults), an optional `conf = <family>[:<share>:<samples>]` field after OS labels in `[tcp:request]` of `p0f.fp`, which p0f writes as `os_family` / `os_confidence` / `os_samples` for client SYNs, and a `ua_family` table in `[http:request]` for the User-Agent signals of `http request` events (`ua_os`, `ua_os_mismatch` against the family of the same connection's SYN, `ua_dishonest`, `http_proxy`); the Kibana objects for it come from a builder script and live in `kibana_export.ndjson`. p0f drops flows after tool (scanner) SYNs on purpose, so those never get HTTP events. The `conf` fields are generated by `docker/p0f/tools/build_os_confidence.py` from public datasets (CC BY 4.0) and must be regenerated after signature changes; scanner signatures stay at the top of `[tcp:request]` (p0f's duplicate check).
- **`tpot` command** (`tpot` launcher at the repo root, package `tpotctl/`): menu + sub-commands for status/`ps`/`images` (the former `dps`/`dpsw`/`dim` aliases now point to them), start/stop/restart, update/restore and the customizer. It is a thin layer: `update.sh`, `restore.sh`, `install.sh`, `uninstall.sh` and `installer/install/deploy.yml` stay the engine and are called, not reimplemented; `update`/`restore`/`customize` hand all options through unchanged. `tpotctl/ops.py` and `cli.py` hold the logic, `app.py` + `screens/` + `widgets/` the Textual UI. The look comes from the T-Pot logo (`doc/t-pot_wallpaper_*.png`): `theme.py` has the colour tokens (magenta `#E20074`, petrol, glass, mist, key, ash, comb, wax) and the one theme `tpot` (no theme switching, on purpose), `glyphs.py` the icon sets `unicode` (default, one cell wide each, tests check it) / `nerd` / `ascii`, `logo.py` the wordmark (lower case `t-pot`) and the honey pot as pixel maps, `splash_anim.py` the two second "honey drip" splash as pure frames (`Splash.frame(t)`, scale 2 when the terminal is big enough; `screens/splash.py` only plays them, `TPOT_SPLASH=off`), `prefs.py` the icon set in `~/.config/tpotce/tpot.json` (`TPOT_ICONS` wins). Rich texts take colours from `theme.color()` and glyphs from `glyphs.g()`, never hard-coded, so `f2` can repaint them. The Status page is fed by `ops.containers()` (honeycomb in `widgets/comb.py`, states from `ops.cell_state()`), `system.py` (/proc) and `events.py` (attacks per minute from Elasticsearch, Suricata / P0f left out); `commands.py` is the `ctrl+p` palette (pages, actions, every setting). `editions.py` switches the edition (`tpot edition set`, *Edition & services*): stop, keep the compose file in `~/tpot_backups`, copy `compose/<edition>.yml`, `TPOT_TYPE=HIVE` for a SENSOR that becomes a HIVE, prune the networks, start; its texts are `installer.EDITIONS`. Scripts and `tpot` commands that the menu runs go through the task screen (`screens/task.py`: `@@tpot` marks of `fuMARK`, read by `runlog.py`; `changed checkout` offers Restart tpot after a failure too, `fail <phase>` turns that phase red; the child run by `engine.py`, a sudo password as a 0600 file for `-B` / `--become-file`); the messages of `tpot` and the customizer come from `say.py`, the same text as `installer/lib/ui.sh`. Keys: up / down move between the settings (`SettingsPane.action_move`; `SettingsForm` and `TpotSelect` drop their own up / down bindings for it), esc goes back to the menu, right / enter into a page. Settings fields are built from the schema (`widgets/fields.py`): `widget` switch / choice / interface / timezone / llm_model / llm_url, `choices` + `custom`, `show_when`, `llm`, `offer` (shown for every edition, problems only warn where the service is absent: the LLM keys), `unlock` (the warning before a fixed system key can be changed: Unlock button, `tpot env set --unlock`, `Settings.change(unlocked=...)`; the keys of `settings.MANAGED_BY` never unlock); tpotinit ignores these keys. The pickers (`screens/pickers.py`) use `netinfo.py` (same detection as `capture-if.sh`, keep both in sync), `tz.py` and `llm.py` (Ollama `/api/tags`, OpenAI `/v1/models`; `discover` / `scan` for an Ollama on 11434, a loopback hit is not offered because the honeypots run in Docker; `test` sends one prompt). The *LLM* page (`LlmPane`) is a `SettingsPane` with its own prefix (`#llm-*`), the LLM keys grouped by honeypot; `tpot llm` is its command. It runs from a venv in `~/.local/share/tpotce/venv` (`tpotctl/bootstrap.py`, standard library only) built from `tpotctl/requirements.txt`: pinned with hashes, wheels only (`pip --require-hashes --only-binary :all:`). The installer links `/usr/local/bin/tpot` and runs `tpot setup`, `update.sh` `fuTPOT_SETUP` refreshes it, uninstall removes link and venv. `tpot` refuses root and only uses `sudo` for `systemctl` (and hands a sudo password as a file to the scripts it runs). Every page of `PANES` says where it works (4th field: `any`, `host`, `hive`, `host+hive`); elsewhere it stays in the menu as a `LockedPane` (why, what instead), its own class is not built there, so nothing calls docker, systemctl or Elasticsearch on macOS / Windows or on a SENSOR. The README matrix of *The tpot Command* names every sub-command with its page and where it works (`test_app.py` checks it). `tpot env list|get|set|check` and the Settings page check against the same `env.schema.yml` as tpotinit (Python in `tpotctl/envschema.py`, writer that keeps both `KEY=value` / `KEY: "value"` forms, comments, owner and mode in `tpotctl/envfile.py`, logic in `tpotctl/settings.py`); they never write a value tpotinit would reject or replace. Both implementations must pass the shared cases in `docker/tpotinit/tests/env_cases.yml` (Python: `tpotctl/tests/test_envschema.py`, bash: `./docker/_tests/run.sh tpotinit_env`). `tpot users list|add|passwd|remove` and the Web users page (`tpotctl/users.py`) manage `WEB_USER`: new and changed passwords are bcrypt via `htpasswd -n -i -B` (password on stdin, never in argv; tpotinit image as fallback), cracklib or 12 characters with confirmation for weak ones, entries T-Pot rejects are marked and repaired by `passwd`, the last working user cannot be removed. They rewrite `data/nginx/conf/nginxpasswd` **in place** (it is bind mounted on its own, a rename would not reach nginx), nginx reads it per request, so no restart. `genuser.sh` is a wrapper on `tpot users add` with the tpotinit container as fallback. `tpot sensors list|add|remove|set|cert` and the Sensors page (`tpotctl/sensors.py`, HIVE only): access is `LS_WEB_USER` (bcrypt, `lswebpasswd` rewritten in place like `nginxpasswd`), the registry `data/sensors.json` holds only metadata and is rebuilt from `LS_WEB_USER` when missing (migration of earlier releases); `add` checks SSH (port 64295 or `--ssh-port`), the hive certificate SANs (renews it with the same openssl parameters as tpotinit if the hive address is missing), grants access first, runs the unchanged `installer/install/deploy.yml` and takes the access back if it fails, then shows the password once; `cert --distribute` runs `installer/install/sensor_cert.yml`. nginx `lsweb.conf` passes the authenticated user as `X-TPot-Sensor`, Logstash `http_input.conf` turns `[headers][x_tpot_sensor]` into `t-pot_sensor`, which `tpot sensors list` aggregates in Elasticsearch (127.0.0.1:64298) for "last seen". `deploy.sh` is a wrapper on `tpot sensors add` with the old steps as fallback.
- **Attack Map** (`docker/elk/map/`): builds from the external `telekom-security/t-pot-attack-map` repo at a pinned tag; `map_data` polls ES and publishes to Redis, `map_web` serves the WebSocket/UI behind nginx.
- **nginx** (`docker/nginx/`) is the single web entry point (port 64297) proxying Kibana, CyberChef, Elasticvue, Attack Map, and the sensor ingest endpoint.
- **Installer**: `install.sh` bootstraps prerequisites and runs the Ansible playbook `installer/install/tpot.yml` (supports multiple distros); `installer/remove/` mirrors it for uninstall.

## Conventions

- Commit messages use conventional prefixes (`feat:`, `fix:`, `refactor:`).
- Shell scripts use the project's `myVAR` / `fuFUNCTION` naming style in many scripts (e.g. `update.sh`); match the style of the file being edited.
- **Keep `tpot` and the customizer in sync.** They build on other parts of the repo, so a change there is not done until the dependent part is updated and its tests pass:
  - Services and editions (new or changed honeypot, ports, networks, any `compose/*.yml`): the `x-tpot` line in `compose/tpot_services.yml`, catalogue and editions consistent, `python3 -m unittest discover compose/tests`. A removed service also goes into `update.sh` `myDROPPED_SERVICES`. A honeypot that talks to no other container joins `honeypot_local` (ICC off, `test_catalog.py` checks it); one with partner services gets a network of its own like `tanner_local`.
  - `.env` keys: change `env.example` and `docker/tpotinit/dist/etc/env.schema.yml` together (same order), and add a case to `docker/tpotinit/tests/env_cases.yml` for a new rule; `tpotctl/tests/test_envschema.py` fails when they drift, `./docker/_tests/run.sh tpotinit_env` checks the bash side. A new rule type needs both `env_validate.sh` and `envschema.py`. Give a new key the control that fits (`widget`, `choices`, `show_when`, `llm`, and `unlock` for a fixed one; `tpotctl/tests/test_pickers.py` checks that every choice is valid and every reference exists). A change to `capture-if.sh` goes into `tpotctl/netinfo.py` too.
  - Installer: the distribution table of `install.sh` (`mySUPPORTED_*`) and `tpotctl/installer.py` (`SUPPORTED`), the editions (`myEDITION` cases ↔ `EDITIONS`), the `@@tpot` marks ↔ `installer.Progress`, the ui block of `install.sh` ↔ `installer/lib/ui.sh` (`tpotctl/tests/test_installer.py` checks all four). A new gum release: new version and both sha256 from its signed `checksums.txt`, in both copies.
  - A new menu page needs an icon in every set of `tpotctl/glyphs.py` (`pane_<key>`, `test_look.py` checks it) and a `REPAINT` entry in `app.py`.
  - Options or prompts of `update.sh` / `restore.sh`: `tpot update|restore` pass them on unchanged, but the help and menu texts in `tpotctl/cli.py` / `tpotctl/app.py` must still match. The menu runs both in the task screen (`-B`, `restore.sh -g` with the groups of `ops.GROUP_TEXT`, whose questions `test_scripts.py` keeps the same as in `restore.sh`); their output goes through `fuUI_*` and their phases through `fuMARK` (a plain fallback block for a checkout without `installer/lib/ui.sh`), no raw `echo "###"` (tests check it). The same holds for every script a person runs: source `installer/lib/ui.sh`.
  - Web users (`WEB_USER`, its format, `nginxpasswd`, the nginx auth config, `genuser.sh`, the web user part of `install.sh`): change `tpotctl/users.py` and `tpotctl/tests/test_users.py` with them. Sensors (`LS_WEB_USER`, `TPOT_HIVE_USER`, `deploy.yml`, `sensor_cert.yml`, `http_output.conf`, `http_input.conf`, the nginx ingest config `lsweb.conf`, the certificate creation in tpotinit): change `tpotctl/sensors.py` and `tpotctl/tests/test_sensors.py` with them.
  - Python dependencies only through `tpotctl/requirements.in` / `requirements.txt` (hashes, wheels only), nothing installed outside the venv besides the distro PyYAML.
  - A new admin task becomes a `tpot` sub-command and/or menu entry, not another standalone script. Every menu pane needs a sub-command (`tpotctl/tests/test_app.py` checks it).
  - Run both `compose/tests` and `tpotctl/tests` (the latter also with the venv for the UI tests).
- CI (`.github/workflows/`) only runs a README link checker and issue housekeeping — there is no automated build or test in CI, so run the relevant smoke test locally.
