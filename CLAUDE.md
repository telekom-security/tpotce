# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

T-Pot is a multi-honeypot platform: ~30 honeypots plus NSM tools (Suricata, p0f) and the Elastic Stack, all run as Docker containers via docker compose. There is no application build in the usual sense — the repo is Dockerfiles, compose files, shell scripts, and an Ansible-based installer. The installed checkout lives at `~/tpotce` on the target host, and many scripts hard-code that path (`$HOME/tpotce`).

## Commands

### Building images (`docker/_builder/`)
- `docker/_builder/docker-compose.yml` is the build-only manifest listing every image (multi-arch amd64/arm64 via buildx). Compose reads `docker/_builder/.env`, but the builder exports the values of the run over it: the version is `-t`, else the file `version`, else `TPOT_VERSION` of the environment, else that of `docker/_builder/.env` (never the root `.env`, never `myUI_VERSION`); the repositories and the defaults `TPOT_BUILDER_ARCH` / `TPOT_BUILDER_JOBS` / `TPOT_BUILDER_LIMIT` are an option, else the environment, else the untracked `docker/_builder/.env.local`, else `docker/_builder/.env`, else the built-in default.
- Build: `docker/_builder/builder.sh` (from any folder; Linux only, `fuUI_LINUX_ONLY` exit 3, `-h` everywhere; any user Docker answers to, `docker info` decides, root (`id -u`) only for the upload limit while pushing; another Docker than root's (`fuOTHER_DOCKER`: rootless, Docker Desktop, any context or `DOCKER_HOST` other than the system socket) gets `-l off` / `--set TPOT_BUILDER_LIMIT=off` instead of sudo, and the QEMU hint names rootful Docker only there; a docker-group member whose Docker is down is told to start it). With no option at a terminal it asks (menu: images all / group / pick, options one by one in their order with the default of the settings preselected, a push without root asks "push without a limit / quit" (quit for sudo, not with another Docker than root's: `fuOTHER_DOCKER`), login, summary with the same run as a `-y` command line, which names every value of the environment or the menu and leaves out only what `.env.local` / `.env` / the defaults say (`myFILES_*`), Build / Back; Builder setup; Settings, each question ≤ 76 columns); with `-y`, any option or without a terminal it never asks. Options: `-i a,b` / `-g honeypots,nsm,elk,tools,all` (union), `-a amd64|arm64|host|both`, `-p` / `--push-hub` / `--push-ghcr` (the existing `docker login`, checked with a 30 s timeout, never asked for: exit 3), `-n`, `-j 1-16`, `-l RATE|off` (tc tbf, only while pushing, only its own limit is removed), `-t` / `--docker-repo` / `--ghcr-repo` (a one-platform push needs its own `-t`, the error names `-a` or the `TPOT_BUILDER_ARCH` it came from), `-T` smoke tests of `docker/_tests/tests` after the build (unless the run builds only this host's platform without pushing, `fuHOST_ONLY`, compose first builds the tested images for this host into docker: no `--load`, compose loads a one-platform build itself; from the cache where the run built this host's platform, after `-n` without it where it did not, e.g. `-a arm64` on amd64, and then the summary warns), `-L`, `--check` / `--setup` / `--uninstall` (buildx builder `mybuilder` + QEMU, always `--builder mybuilder`; buildx keeps builders per user, so `--check` / `--uninstall` say whose builder they handled (`fuWHO`) and name the other one (`fuOTHER_BUILDER`: as a user the sudo hint, as root under sudo the builder in the store of `SUDO_USER` via `getent`); platforms of buildx matched as whole entries, `fuHAS_PLATFORMS`, the same in `--check`, the run and the status line), `--set KEY=VALUE` / `--unset KEY` / `--show-config` (settings in the untracked `docker/_builder/.env.local`, `TPOT_BUILDER_ENV_LOCAL` in tests: `TPOT_DOCKER_REPO`, `TPOT_GHCR_REPO`, `TPOT_BUILDER_ARCH`, `TPOT_BUILDER_JOBS`, `TPOT_BUILDER_LIMIT`; read as text, a UTF-8 BOM ignored; the new text is made in full, then written in place by the shell (`fuWRITE_IN_PLACE`: inode, mode, owner, comments, CRLF and BOM stay), a failed write puts the old text back, a signal waits until the file is whole, exit 3 with a `chown` hint; a key the environment overrides gets a warning; the version is no setting). An option of a build next to `-L`, `--check`, `--setup`, `--uninstall`, `--set` / `--unset` is a usage error (`--show-config` takes them). `-y` is no build option (fine next to `--setup` / `--check` / `-L` / `--set`). The menu keeps the items in their order with the default preselected (`fuUI_CHOOSE --selected`), asks yes / no with `fuUI_CONFIRM --default no`, starts each round anew after Back and prints its command lines with the builder's full path (`mySELF`). For the upload limit, "another Docker" than root's under sudo (rootless, Docker Desktop, any context or `DOCKER_HOST` other than the system socket: `fuOTHER_DOCKER`) gets `-l off` / `--set TPOT_BUILDER_LIMIT=off`, never sudo. A `.env.local` with a NUL byte (UTF-16) is never written (rc 3). A one-platform push (`-a amd64|arm64|host` with `-p` / `--push-*`) needs a `-t` that is no plain version (`^v?[0-9]+(\.[0-9]+)*$`, i.e. `<version>-arm64`), else exit 2; the menu asks again. An `.env.local` that is no text (a NUL byte, UTF-16) stops every run, `--show-config`, `--check` and the menu with exit 3. Exit 0 / 1 image failed / 2 usage or setting / 3 environment / 4 smoke test / 130 cancelled. Compose runs with `-f docker/_builder/docker-compose.yml` plus a generated `log/override.yml` / `override-load.yml` (`platforms: !override`, `tags: !reset []`, needs compose ≥ 2.24.4, checked for `-a`, a push to one registry and the smoke-test build); logs in `docker/_builder/log/` (`TPOT_BUILDER_LOG_DIR`; a run removes the old overrides and empties `builder.log`, the logs of the images it builds, `load.log` when it makes that build and the logs of its tests); under sudo `fuEXIT` (EXIT trap + `fuCANCEL`, once, INT / TERM ignored from its start) removes the limit and chowns the logs back to `SUDO_UID:SUDO_GID` (`chown -R -h` of the resolved path, `fuREAL_PATH`, only when its real parent belongs to that user). The groups (`fuGROUP_IMAGES`) must cover the compose file. builder.sh speaks through `installer/lib/ui.sh` (plain fallback block) and can be sourced for its functions; tests in `tpotctl/tests/test_scripts_builder.py` (stubs for docker incl. `info` / `info --format`, id, uname, chown, tc, ip, getent). `setup_builder.sh` is gone. It is a tool for building releases and on purpose **not** part of the T-Pot Manager: no menu entry, no sub-command, not in the README matrix (`test_scripts.py` `BuilderTest` checks).
- Build one image: `cd docker/_builder && docker compose build <service>`, or `cd docker/<service> && docker compose build` (each service dir has its own standalone `docker-compose.yml` with `build: .`).

### Smoke tests (`docker/_tests/`)
Post-build container tests; they require the image to already exist locally and never build.
- All: `./docker/_tests/run.sh`; list: `./docker/_tests/run.sh --list`
- One: `./docker/_tests/run.sh cowrie` or directly `./docker/_tests/tests/cowrie.sh [--image ...] [--<proto>-port ...]`
- Options: `--timeout SEC`, `--bind-ip IP`, `--keep-artifacts`
- Cowrie personas (no Docker): `python3 -m unittest discover -s docker/cowrie/tests -t docker/cowrie`
- `run.sh`, `lib/common.sh` and every `tests/*.sh` clear CDPATH before their first `cd` (`tpotctl/tests/test_smoke_harness.py`, which also checks every `*.sh` of the checkout that captures `$(cd …)`); a new test starts with `unset CDPATH` before its `SCRIPT_DIR` line.
- Conventions for new tests: one executable `tests/<service>.sh` per honeypot, source `lib/common.sh` (`test_*` helpers for compose, port checks, waiting on log text, cleanup), bind to loopback, prefer dynamic host ports, temp files under `/tmp`, fail with an image build hint when the image is missing. Some tests need host tools (e.g. dicompot needs DCMTK).

### T-Pot ISO preview (`installer/iso/`)
- Build: `installer/iso/build.sh` (no options at a terminal: gum menu themed like `docker/_builder/builder.sh`, via `installer/lib/ui.sh`; every choice is also printed as its command line, `fuCOMMAND_LINE`) or `-a amd64|arm64|both [-b <branch>] [-r <repo-url>] [-i <netinst>] [-o <folder>] [-D] [-d <device> [-y]]` (Docker by default outside Linux; exit 0 / 1 failed / 2 usage / 130 cancelled; re-execs Homebrew bash ≥ 4 on macOS; installs a pinned, sha256-checked gum for macOS into `~/.local/share/tpotce/bin` — `myGUM_DARWIN_VERSION` must equal `myUI_GUM_VERSION` of `ui.sh`). It remasters Debian's current 13 netinst, verified via `SHA512SUMS` signed by the pinned Debian CD key, with xorriso `-boot_image any replay` (boot records, Secure Boot loaders untouched; `fuCHECK_ISO` compares them without block addresses). `isotree.py` puts "Install T-Pot" first (GRUB, ISOLINUX, themes, splash, `md5sum.txt`) and stops on any unexpected netinst layout. `myDEBIAN_MAJOR` must match the Debian version gate of `install.sh`. Output goes to `installer/iso/out/` (gitignored): ISO + `.sha256` + `.sha512` + `.buildinfo`; the netinst cache `out/cache` (`TPOT_ISO_CACHE`) follows Debian's signed `SHA512SUMS` on every run (new point release replaces, damaged re-downloaded, `.part` resumed).
- Offline payload: the ISO carries T-Pot (`fuSNAPSHOT` / `fuSNAPSHOT_GIT`: one shallow commit of `-b` / `-r`, from this checkout when `-b` / `-r` are its branch and origin (its last commit, uncommitted changes only warned about) or it has the commit, else fetched from the repository; a branch keeps its upstream for `update.sh`; the commit must have `tpotctl/requirements.txt` and `installer/lib/ui.sh`), packed by `isotree.py gittar` (sorted, root-owned, no xattrs of macOS) as `tpotce.tar`, the Linux gum of the pin in that commit's `ui.sh` (`fuGUM_LINUX`, sha256 checked) and the wheels of its `requirements.txt` for the Python and the glibc of the ISO's Debian (`fuWHEELS` with the netinst: `fuDEBIAN_GLIBC` reads X.Y of the one `libc6_*_<arch>.deb` in its pool with `xorriso -find`, `fuDEBIAN_CODENAME` its `.disk/info`, `fuDEBIAN_PYTHON` asks `api.ftp-master.debian.org/madison` for python3 of that codename once, parsed by `isotree.py debian-python`, kept as `out/cache/debian-<codename>.python`; no table per Debian, a new major is only `myDEBIAN_MAJOR`; `isotree.py requirements`, `pip download --only-binary :all:` into an empty folder, on a missing wheel the hint to raise `tpotctl/requirements.in`; both in the `.buildinfo` as `wheels_python` / `wheels_glibc`; the Docker build image is `debian:<myDEBIAN_MAJOR>-slim`); `iso.conf` names `TPOT_REPO_URL`, `TPOT_BRANCH`, `TPOT_COMMIT`. The build host needs git and pip (the Docker image has both).
- USB: `-w <iso> [-d <device>] [-y]`, `-l`. Candidates come only from `fuUSB_LIST` (Linux `lsblk -dpnbP`, values decoded with `printf %b`, never evaluated: TRAN usb/mmc or RM=1, not RO; macOS `diskutil list -plist external physical` + `info -plist`: not internal, not virtual, writable) minus `fuPROTECTED` (the disks of `/`, `/boot`, `/boot/efi`, `$HOME`, the out/cache folders and the ISO's folder; APFS physical stores resolved). The ISO is checked against its `.sha256`, written with `dd` (raw `/dev/rdiskN` on macOS, sudo only if not writable), read back (`fuSTICK_CHECK`: rc 1 mismatch, 2 unreadable) and ejected.
- Release (maintainers): `-R [-s <gpg-key>] [-U <tag>]` — clean checkout, branch pushed and equal to the remote (`fuRELEASE_CHECK`; a tag or commit is refused because `update.sh` needs a branch), both architectures into `out/release-<version>/`, `SHA256SUMS`/`SHA512SUMS` written all-or-nothing (`fuWRITE_SUMS`), optional detached armored signatures verified via `VALIDSIG` of the key's fingerprint, optional `gh release upload --clobber` of exactly the files of the run. An earlier release build in the folder is only replaced after a confirmation or `-y`.
- Payload `/tpot` on the ISO: `preseed.cfg` answers only safe questions (no partman, GRUB, users, passwords or locale; hostname and proxy `seen false`; adds the packages of the installer, a superset of `myPACKAGES_DEBIAN` of `install.sh`, `PreseedTest`, and those of the graphical terminal), `early.sh` (the `early_command`, `sh /cdrom/tpot/early.sh` before the udebs load: it teaches the installer virtio keyboards and starts a detached watcher that puts the name `tpot` into the reserved names of user-setup once its udeb is there, so the account dialog is meant to refuse it; the T-Pot installer refuses the name anyway; `EarlyTest`, `ReservedNameTest`), `late.sh` (busybox sh) copies `install.sh`, `start.sh`, `terminal.sh`, `prepare.sh`, `iso.conf`, `version`, `ui.sh` (of the checkout that built the ISO), `tpotce.tar`, gum and the wheels to `/usr/local/share/tpot-iso`, the login hook `profile.sh`, `tpot.issue` and the unit `tpot-iso.service` into the target and runs `prepare.sh` in it (`in-target`) for the user of `passwd/username`: `~/tpotce` from `tpotce.tar` (HEAD must be `TPOT_COMMIT`, an existing one is kept), gum into `~/.local/share/tpotce/bin`, `tpot setup --wheels` as that user, the sshd drop-in of `AcceptEnv`, the drop-in `tpot-iso.service.d/user.conf` (`User=`) and the link in `multi-user.target.wants` (`fuSERVICE`; not for the user `tpot`, `TPOT_ISO_SYSTEMD` in tests); log `/var/log/tpot-iso.log`; a failure there does not stop the installation, the T-Pot installer then gets what is missing. `install.sh` then skips what is there (`packages_installed` via `dpkg-query`, the clone, the venv: `bootstrap_needed`). After the boot `tpot-iso.service` (until `tpot.service` exists; `ExecCondition` skips it without a screen: no `/dev/dri/card*` / `/dev/fb*` and no VT in `/sys/class/tty/console/active`, a serial console alone, where `tpot.issue` names the login; the devices count because arm64 with SPCR lists only its UART there; `PAMName=login` on `tty8` for a logind session, `chvt 8` before, `chvt 1` after, `TPOT_ISO_CONSOLE=1`) runs `start.sh` without a login. On a screen (the service, a login on a VT: `fuVT`; not SSH, `DISPLAY` / `WAYLAND_DISPLAY`, `TPOT_TERMINAL=off` or a pty, those run it in place) `fuWATCH` runs itself in `terminal.sh` (`fuX_RUN`, a background job on `<&0`) and watches it: X within `TPOT_ISO_X_WAIT` s (30; the inner run touches `TPOT_ISO_RAN`), the key S there within `TPOT_ISO_KEY_WAIT` s (60; `fuWELCOME`, Enter does not count, touches `TPOT_ISO_SEEN`); otherwise it stops the terminal (`fuUI_STOP`, `fuVT_TEXT` puts the VT back to text mode and its keyboard) and asks on the text console, as where it cannot start (`fuGRAPHICAL`: its packages, no graphics device under `TPOT_ISO_DEV`, the text console chosen in this boot): graphical terminal (again), text console (the flag `TPOT_ISO_TEXT`, `/run/lock/tpot-iso.text`, until the reboot; `TPOT_ISO_PAUSE`: Enter before the console closes) or later. An interactive login of a sudo user (`profile.sh`) runs it too. `start.sh` speaks through `ui.sh` (its own copy in the share, else that of `~/tpotce`), reads `iso.conf` (never sourced, values validated with the same regexes as `build.sh`, `test_build_and_start_accept_the_same_source`), over SSH offers a true colour test (`fuCOLOR_TEST`, saved with `prefs.save`), and at a terminal asks which T-Pot (`fuDIALOG`): the one of the ISO (Enter; no terminal: always), the newest commit of its branch (`fuNEWEST_LOOKUP` `git ls-remote --exit-code`: rc 2 means the remote has no such branch and gets its own warning, only no answer is "cannot be reached"; `fuNEWEST_FETCH` fetch + reset of the untouched `~/tpotce`; a failed fetch asks for the ISO's), or another branch/repository (`fuOTHER`, or `start.sh -b <branch> [-r <repo>]`) checked with `git ls-remote` (missing branch/unreachable repo refused, tag/commit only after a confirmation), cloned into `~/tpotce` (an existing one only if origin and branch match; the untouched T-Pot of the ISO, `fuISO_CLONE`, is moved aside meanwhile and put back if the clone fails) and that clone's own `install.sh` runs; all get `TPOT_WHEELS` for `tpot setup`, after the dialog `TPOT_INSTALL_CONFIRMED=1` (`install.sh` then skips its "Start the T-Pot installer?" / "Install?" and unsets it). One installer at a time: `fuLOCK` (flock on fd 9, which `install.sh` inherits; `TPOT_ISO_LOCK`, pid + where in the file, a dead pid is stale) after the choice, `fuBUSY` before the dialog. Never as root or as the user `tpot`; done (`TPOT_ISO_INSTALLED`, `tpot.service`) says so and ends.
- Branches in the menu: *Source* lists the repository's branches (`fuBRANCHES`: `ls-remote --heads`, master and dev first, names `fuVALID_BRANCH` refuses left out), takes another repository or a tag/commit; `fuREMOTE` reports `ok|tag|commit|missing|unreachable|differs|nogit`, everything but `ok` is a warning (a tag/commit: `update.sh` cannot update such a T-Pot).
- Tests (no Docker, no download, no real disk; stubs for lsblk/findmnt/diskutil/df/dd/gpg/gh/curl, the menu in a pty on a copy of the tree): `python3 -m pytest tpotctl/tests/test_iso.py -q`. `build.sh` can be sourced (functions only) for such tests.

### On a running T-Pot host (from `docker/tpotinit/dist/bin/`)
- `tpot check honeypots [--only a,b] [--no-geo] [--keep] [--timeout S] [--dry-run] [-B file] [-y]` (`tpotctl/checks/run.py` `Check`, stages in `stages.py`): inventory → `EwsHold` (fails: exit 3, nothing probed) → probes on the host's own address (`run.probe_address`, not 127.0.0.1: docker-proxy changes the source port) → one geo event per running honeypot (`fixtures.render` with a fixed test IP, IPv4 only, marker port 51234 + n, appended through `logfile.py`: folder fds, O_NOFOLLOW, one link, never created; root through `sudo -S` with the `-B` file on stdin where the user may not) → the stages polled (port, answer, log line by token / own address + source port / dicompot's time window, ES doc and GeoIP on 127.0.0.1:64298, Redis + WebSocket of the Attack Map, ewsposter held; ✓ ✗ – ·; a knock may leave no trace: –) → settle (15 s, or the longest `probes.LATE_WRITE` of the probed honeypots + 10 s: ddospot and ciscoasa write 60 s late, their log stage waits for it) → end of the hold → cleanup unless `--keep`, Elasticsearch only, two passes 60 s apart (`stages.cleanup_query` / `OwnEvents`: `@timestamp` from the run start to the pass + 1 min and `type` ∈ the probed / injected types (never Suricata / P0f), and (a) the token by `query_string`, (b) a test IP with the marker port of its injection (a fixture without `{src_port}`, `GeoEvent.marker` False: the test IP and its type in the window), or (c) the probe source with a recorded source port, only where the ports survive: an IPv4 address of the host, not docker-proxy; never by an own address alone; the probe events none of them names are counted, `cleanup.left` + a Kibana link; the token clause is dropped only on Elasticsearch's "cannot run this query" errors, `ElasticError.token_refused`; the delete waits up to 60 s) → `~/.local/share/tpotce/checks/last.json` (format in the docstring of `run.py`) → only then the output of the end; every line also in `last.log`, a closed stdout never stops the run. SIGTERM / SIGHUP become `Terminated` like Ctrl+C (`run.Signals`, set before the hold is taken, only the first signal raises, the handlers before come back). A SENSOR runs stages 1–3, the others say "check on the HIVE". It asks first (`run.question`), `-y` confirms, no terminal and no `-y`: exit 2; 0 ok, 1 a stage failed (or an error before the hold: last.json with the error, no honeypots), 130 cancelled (INT, TERM, HUP). `tpot check pipeline` is the same with `geo_only` (no probes); a SENSOR refuses it (exit 2). The probe table (`probes.py`) leaves ports out with a reason (`not_tried`: dionaea 20; dionaea's TFTP 69/udp is read with an unconnected socket, `from_any`, because its answer comes from a port of the session), knows the sources a honeypot does not log (`PortProbe.ignores`: log + ES n/a where the ports survive; no entries today, the `blacklist` of elasticpot / ipphoney / rdphoneypot in their `dist/honeypot.cfg` is `127.0.0.1` only, their fallback without it would leave out 192.168.0.0/16 too), matches conpot_ipmi by address (`ADDRESS_ONLY`), gives the map n/a for `NO_DEST_PORT` and waits `MAP_WAIT` after Elasticsearch; `cleanup.left` also counts the sourceless events of `SOURCELESS_TYPES` (Dicompot). Before its first probe / geo event a run writes `checks/pending/<run id>.json` (0600 in 0700, fsynced; a failed first write: exit 3), removed after a cleanup that ran through; `tpot check cleanup [--dry-run] [-y]`, the *Remove them now* button of the *Checks* page and every check (before its hold) run the pending ones (one pass, under the lock of the checks; a running check: nothing, exit 0), each file bound to its run (`read_pending`: start ↔ run id, capped window, source = host, types ⊆ inventory, ports, test IPs; anything wider is refused and kept) and recorded in that run's last.json (`note_cleanup`).
- `hptest.sh [-B file] [-y] [--nmap] [--tools-only] [host]` — `exec ~/tpotce/tpot check honeypots` where `tpot setup` works and the host is this one; otherwise, for another host, with `--nmap` (the Checks page) or `--tools-only`: service requests and nmap over the ports of `~/tpotce/docker-compose.yml` (ports from `docker compose config --format json`, the tools per distribution from `fuTOOLS_FOR`).
- `attackmap_pipeline_test.sh [--types ...] [--timeout S] [--dry-run] [-y] [-B file]` — `exec tpot check pipeline` (`--types` → `--only`) where the T-Pot Manager runs; its fallback is the old end-to-end check: injected honeypot JSON → Logstash → Elasticsearch → map_data → Redis → map_web WebSocket, events not cleaned up, their source IPs only the fixed test IPs of `myFALLBACKIPS` (`fuPICKIPS` asks Elasticsearch for nothing). A wrong option of either script is exit 1, `-h` exit 0.
- Both run under the hold of ewsposter (`ews_hold.sh`, the same as `tpotctl/checks/ewshold.py` `EwsHold`): flock on `<data>/ews/check.lock` without waiting (one check at a time), the marker `<data>/ews/hold`, a `hold.ack` written after it within 180 s or nothing is probed (exit 3), the marker looked at every 30 s and written anew every 5 min (a marker someone else removed, i.e. a T-Pot start, or two failed renewals stop the check: `EwsHold.check()` raises `HoldError`, the bash loop sends TERM to the script), removed at the end (EXIT / INT / TERM, after a 10 s settle for the last log lines; hptest.sh first stops its scans and waits for them); ewsposter in the compose file but not running: the marker without waiting for an ack (it starts held); docker cannot tell: as running; not in the compose file: no marker; a dry run needs no hold. In bash every create, open and unlink in `<data>/ews` goes through python3 and the folder fd, the lock is held by a python3 process on a pipe from the script; `ews_hold.sh run` puts COMMAND in a process group of its own and stops the whole group. `hold.state` (`<normal|held|stuck> <epoch>`, older than 2 min = unknown) is `ewshold.ews_state()`; `EwsHold.check()` also stops the check when the marker is gone or older than 25 min (suspend, clock step) or hold.state says normal. `hold.ack` may name modules whose idle passes keep failing (a line `failed: <module> ...`; ews.cfg sections, conpot = conpot_*): their honeypots get no probe and no geo event (stage 7 ✗), re-read before each probe / geo event. When the marker is gone (removed or expired), ewsposter's entrypoint quarantines every module that was not clean and caught up in the last idle round: normal passes run with a config copy where it is false, it gets one idle `-m` pass per round until one is clean and caught up; `/data/ews/quarantine` names them (`ewshold.ews_quarantine()`, the page: "sends, except …"). A check that ends without a running ewsposter having confirmed its hold leaves `<data>/ews/catchup` (written when the hold starts without a running ewsposter); the entrypoint treats it, a hold.state held / stuck without a marker, or a start without `ews.idx` (a new container) as the end of a hold: an idle round first. tpotinit clears hold, hold.ack, quarantine, catchup and a check.lock no check holds.
- The *Checks* page (`ChecksPane`) runs `tpot check honeypots -y` / `tpot check pipeline -y` in the task screen after a `ConfirmDialog` with `run.question` (switches *Geo probe* → `--no-geo`, *Clean up afterwards* → `--keep`, `--become-file`), a dry run and `hptest.sh --nmap [host]`; after the task it reads `last.json` again (`run.read_result` / `result_view`: checked, a broken file is one line, never a traceback) into a `NavDataTable` (`sync_rows`, which compares a cell's own style too; a column per entry of `stages` titled by `stages.SHORT_TITLES` so it fits at 80 columns, `fixed_columns=1`, a legend with the full `titles` below; glyphs `stage_*` of `glyphs.py`; on a SENSOR the geo, cleanup and pipeline controls are disabled), enter on a row opens `CheckDetailDialog` (values of last.json as plain text); `ewshold.ews_state()` gives its ewsposter line (stuck is a warning). The scripts run in the task screen too, in the look of `installer/lib/ui.sh` with `fuMARK` phases (a plain fallback inside the tpotinit image); `tpot check` prints `@@tpot phase|warn|fail` marks with `TPOT_MARKS=1`. `mytopips.sh` is `tpot attackers`.

### tpot command and its tests
- `./tpot -h` lists the sub-commands; `./tpot setup` builds the venv.
- `python3 -m unittest discover tpotctl/tests` runs the non-UI tests; the Textual UI tests are skipped there and run with the venv: `~/.local/share/tpotce/venv/bin/python -m unittest discover tpotctl/tests`.

### Shared sudo-mode backend

- `uninstall.sh` uses `sudo_mode.stage_uninstall` to copy the shared play, `sudo_reconnect.yml`, module and private credential to0700 staging under `/tmp`. Its last privileged shell deletion precedes `safe_remove` with `tpot_cleanup_install=true`; the system Ansible/Python stay installed. The optional backup gets the same private credential. `--keep-sudo-rule` works in the shell, CLI and uninstall screen; unknown/unsafe alternatives retain the grant with a warning. The remove play exposes the operation only via `[never, tpot_sudo]`. EXIT/cancellation clean staging and transferred password files, cleanup failures are visible and nonzero, and failed Manager exec removes its collected password. Real integration replaces only package/service removal, not sudo, checkout deletion or the final staged play.
- `SettingsPane` has the Host sudo block (not the LLM subclass); `SensorsPane` offers Sudo mode without another column. `screens/sudo.py` collects all answers before a noninteractive CLI task, whose `Task.secrets` become private files; neither `Task` nor `SudoChoice` includes passwords in repr. Account-check failures block secure and are shown explicitly. Polling only uses the existing unprivileged local passwordless check (failure means unknown), never SSH or a password prompt. The dialog and page controls follow arrow navigation at80x24 (`test_sudo_ui.py`, `test_nav.py`).
- `installer/install/sudo_mode.yml` is the common Ansible entry point; its local module `library/tpot_sudo.py` owns privileged checks and changes. `tpotctl/sudo_mode.py` only validates private password files, builds the command and reads results. Actions: `status`, `secure`, `convenient`, `safe_remove`; play variables: `tpot_sudo_action`, optional `tpot_sudo_user` (otherwise the connection user), `tpot_user_password_file`, `tpot_keep_sudo_rule`, `tpot_sudo_result_file`. The result file is private JSONL, one record per host (`schema: 1`, `host`, `result`, `error`, `changes`); failed operations retain any already completed changes.
- The backend locks `/run/lock/tpot-sudo.lock`, checks `passwd -S`, evaluates `LC_ALL=C sudo -ll -U USER`, and uses `sudo -n -k` for its access probe (never the credential cache). Only an exact root-owned 0440 UID rule at `/etc/sudoers.d/tpot` or `tpot-install` is its own; neither is an alternative grant. Unknown policy formats/restrictions refuse removal. Normal users follow `UID_MIN` from `/etc/login.defs`. Secure establishes a usable password and verified sudo/wheel access before removing the permanent grant; foreign rules stay untouched, and effective passwordless access is reported honestly. Rule changes use `visudo`, atomic publication/rollback and deferred termination during validation. `safe_remove` never sets passwords or adds groups; it keeps the rule with a warning unless removal is already safe. The temporary installer rule remains until its parent cleans up.
- Portable tests: `python3 -m unittest tpotctl.tests.test_sudo_mode`. The `LinuxModeTest` cases deliberately mutate accounts and sudoers and run only as root in a **disposable Docker container**, with `TPOT_TEST_SUDO=container-only`, sudo, ansible-core, cracklib-check and shadow account tools installed. Mount only the test, module, controller and play sources, not runtime configuration. Never opt a production container into these tests.
- Ansible's native password-file reader strips all edge whitespace. Controller commands instead set `ansible_become_password` through a file lookup with `lstrip=false, rstrip=false`, removing only one final newline; argv holds the expression and path, not the password. `install.sh -B` uses Ansible's password stdin, which preserves spaces. `-B -` gets its own0600 file and an abortable reader; EXIT cleanup waits for that reader and removes only its own files. File checks run before Python/the clone is available, using base-system tools; xtrace is disabled while the password is in shell variables. Explicit `-B` remains available even when sudo initially needs no password.
- The installer runs the common play twice: `tpot_sudo_prepare=true` validates the mode and, for secure, prepares the password/group without changing the rule; the final call follows image pull and privileged diagnostics. `tpot.yml` also exposes the play via the explicit `tpot_sudo` tag (`never` by default). The marks `sudo_prepare` and `sudo` use the Ansible log; their tasks do not inflate the main playbook's progress count.
- Only the final installer call sets `tpot_cleanup_install=true`. The backend tries the root-parent lock nonblocking (it already holds the common sudo lock), keeps an active parent's grant, and otherwise removes only verified owned temporary/boot files. An unsafe removal keeps the grant with a warning, but removes its owned boot deletion instruction to avoid delayed lockout. Preparation and status never clean up. Binary checks in install.sh use `type -P sudo`, so its password wrapper cannot hide a missing executable on a root start with `-B`.
- `tpot sudo` and `tpot sensors sudo` use `sudo_mode.execute` with private results and the shared play, never a second rule implementation. All selected targets are checked before successful ones change; per-target errors make the command fail, and drift does not block sudo management. Provided passwords are validated then copied with `installer.secret_files`, not passed in argv; the CLI copies each context's mapping before combining files so it never changes cleanup ownership. A changed SSH target reconnects through a conditionally included `sudo_reconnect.yml` (Ansible's `reset_connection` ignores its own `when`), otherwise a persistent connection retains the old groups. Local group additions warn that existing sessions need a new login. Real SSH tests additionally need openssh-server and mount sudo_reconnect.yml; server, keys and control socket are private disposable-container fixtures.
- Classic and assistant installs require an explicit More secure / More convenient choice (a neutral first item in gum, `Select.NULL` in the assistant); `-s` defaults secure and `--sudo-nopasswd` is an explicit answer. `Answers.sudo_mode` starts empty and `engine_command` refuses it. Account state is read without privilege through `passwd -S`; unknown is never treated as usable. Secure collects and checks a missing user password before writing configuration; actual password/group/rule changes still belong solely to the common play. Bootstrap sudo input is kept in a private file and forwarded through `tpot install --become-file`; the new-user password and explicit mode are forwarded too. `secret_files` removes all its files even if one removal fails and reports leftovers; the assistant shows this as a failed run. The Linux account-state test additionally mounts installer.py, runlog.py and bootstrap.py as source.
- Root starts require a saved `install.sh --user NAME`, not inline shell source. The parent stages private0400 inputs and a root-owned0600 backend under `/run/tpot-install`, holds its own installation lock, and runs the child via runuser with that user's HOME/cwd (root's XDG/Python/sudo environment is removed). Root prepare/cleanup and `tpot-install-cleanup.service` use the same Python backend and shared locks; the parent passes its verified inherited installer-lock fd, never bypasses locking. The guarded boot service pins the original user/UID and checks the digest of its root-owned0600 helper in `/var/lib/tpot-install` before execution. Rules are removed only after verified remaining access, with rollback on invalid policy; foreign files and unsafe-to-remove grants stay with an explicit error. Cleanup stops the child tree first. Locked accounts get their group after their password in the common play. Python3 is installed before root handover if absent. The old Debian `su` path creating a personal rule is gone. Root integration tests additionally need install.sh, README.md, tpot.yml, procps, systemd, coreutils and ansible.posix, still only in a disposable container.
- After changing `installer/install/library/tpot_sudo.py`, run `python3 -m tpotctl.sudo_mode` to regenerate its byte-identical readable data block in install.sh; `--check` and `test_sudo_mode.CopyTest` enforce the single source. The complete installer exceeds Linux's single-argument limit: the README bootstrap downloads to a private temporary file instead of placing the source in `bash -c`, preserves stdin for questions and propagates failures.

### Release
The file `version` at the repo root is the one source of the version number. Scripts and the T-Pot Manager read it (`fuUI_VERSION`; on an installed T-Pot `TPOT_VERSION` of `.env` as fallback) and never carry the number themselves. The places that cannot read it (the `TPOT_VERSION` of `env.example` / `.env` / `docker/_builder/.env`, the image tags of `docker/*/docker-compose.yml`, `CITATION.cff`, the landing page, the smoke test defaults, the p0f examples) are the table `PLACES` in `tpotctl/release.py`: `python3 -m tpotctl.release check` compares them with `version` (exit 1 with the list), `python3 -m tpotctl.release set-version X.Y.Z [--root DIR]` writes `version` and every place (in place: modes and line endings stay; `date-released`, CHANGELOG, README, SECURITY.md stay for you). Places that name a version on purpose (history comments, docs, test data, deprecated services) are in `EXCLUDED` with their reason; `tpotctl/tests/test_release.py` fails on a hard coded number that is in neither table, so a new one goes into a table or reads `version`.

## Architecture

- **`tpotinit` is the orchestrator.** Every compose file starts with the `tpotinit` service (host networking, NET_ADMIN, docker socket, mounts `${TPOT_DATA_PATH}` as `/data`); all other services `depends_on` it being healthy. Its `docker/tpotinit/dist/entrypoint.sh` validates `.env` (rules in `dist/etc/env.schema.yml`, read with `yq` by `dist/bin/env_validate.sh`; all errors at once, service settings only if the service is in the compose file), creates/permissions the data folder (`dist/bin/data_modes.sh`, sourced by `entrypoint.sh` and `clean.sh`: folders 770, files 660, nginx `conf` / `cert` 774 / 664, one `chmod -R u=rw,g=rw,o=,ug+X` per path, which needs the X of busybox / GNU chmod; a path that is a link is skipped; smoke test `tpotinit_modes`), sets up web users (`create_web_users`: `nginxpasswd` / `lswebpasswd` from `WEB_USER` / `LS_WEB_USER`, in place; on a HIVE a line whose user the `.env` no longer names goes into `<file>.lost` first, never twice, with a warning; a line that cannot be kept (`.lost` a link or no regular file, a failed write) leaves the file as it is and stops the start like a failed validation; a HIVE without `WEB_USER` names how many lines `nginxpasswd` still holds before it aborts; smoke test `tpotinit_users`), blackhole routes, iptables NFQ rules (for glutton/honeytrap), interface config for the NSM services, marks the first import of the Kibana objects pending on a fresh install (`kibana_objects.py mark-fresh`, before `/data/uuid`), starts the job `dist/bin/kibana_objects.sh` in the background on a HIVE with Kibana (next to `es_retention.sh`, its PID in `cleanup`; it waits for Kibana and runs `kibana_objects.py apply --mode "${TPOT_KIBANA_OBJECTS:-keep}"`, see *Kibana objects*), and runs autoheal. The capture interface comes from `dist/bin/capture-if.sh` (`TPOT_CAPTURE_INTERFACE` or the route to the internet); identical copies live in `docker/{suricata,p0f,glutton}/dist/` and must be kept in sync. Host-side helper scripts ship inside this image under `dist/bin/`.
- **Editions are compose files in `compose/`.** `standard.yml`, `sensor.yml`, `mini.yml`, `llm.yml`, `tarpit.yml`, `mobile.yml` (MAC_WIN is gone: `customizer_core.REMOVED_EDITIONS`, the customizer refuses its files with a hint). The root `docker-compose.yml` is the active one and is a copy of `compose/standard.yml` — keep them in sync when editing the standard edition. `tpot_services.yml` is the service catalogue that `compose/customizer.py` (logic in `customizer_core.py`, UI-free `State` + text dialog in `customizer_tui.py`, full screen dialog in `tpotctl/screens/customizer.py`; headless/`--rebuild` need only stdlib + PyYAML, Python ≥ 3.9, the distro package comes from the installer / `update.sh` `fuCUSTOMIZER_DEPS`, else the tpot venv) uses to build a custom compose file: an edition as base plus added/removed services and host-port overrides, written into a `# customizer:` header with a sha256 of the body so `update.sh` (`fuRESTORE_CUSTOM`) can `--rebuild` it on updates unless it was hand-edited. `customizer.py --adopt FILE [--report]` turns a file of the customizer before v2 (`# T-Pot: CUSTOM EDITION`, rebuilt without a question) or a compose file of your own (adapted only after a yes, `update.sh --adapt-compose` without a terminal) into such a selection of the release and reports what it does not carry over (`update.sh` `fuADOPT_COMPOSE` / `fuADOPT_RUN`; `--rebuild` and `--adopt` both run with `fuCUSTOMIZER_PYTHON`, the venv of the T-Pot Manager where there is one). Every catalogue service needs an `x-tpot` line (group, description, optional requires/conflicts/hidden/hive_only/required); editions may only differ from the catalogue in ports, networks and depends_on. Run `python3 -m unittest discover compose/tests` after touching any compose file. Adding/changing a service usually means touching several of these files plus `docker/_builder/docker-compose.yml` and `docker/<service>/docker-compose.yml`.
- **Configuration**: `.env` (defaults in `env.example`) feeds both compose variable substitution (`TPOT_REPO`, `TPOT_VERSION`, `TPOT_PULL_POLICY`, `TPOT_DATA_PATH`, ...) and tpotinit (`TPOT_TYPE=HIVE|SENSOR`, `TPOT_BLACKHOLE`, `TPOT_HIVE_*`, `WEB_USER`, ...). Root `.env` and `docker-compose.yml` are generated runtime configuration, not tracked by Git. The installation assistant previews `env.example` in memory and creates a private `.env` only after confirmation; `install.sh` generates the selected compose file. `generated.py` stamps the release sources, not local values; the customizer's shared writer and edition switches stamp their outputs too. Keep the source marker outside the customizer's checksummed body and never make a hand-edited body appear unchanged when restamping.
- **Self-managed compose**: `generated.configuration_status` warns rather than blocks for files without leading T-Pot/customizer metadata. Env source checks remain active; missing files and malformed generated metadata still block. Settings validation, the Settings/LLM status line and the Git-hook check show the notice. Never stamp newer sources onto a customizer file that update restored without rebuilding.
- **Per-service layout**: `docker/<service>/{Dockerfile, docker-compose.yml, dist/}`. Containers are generally `read_only` with tmpfs, run as uid/gid 2000, and write logs to `${TPOT_DATA_PATH}/<service>/log`. Image tags follow the file `version` (see *Release*).
- **Data flow**: honeypots write JSON/log files under `/data/<service>/log/` → Logstash (`docker/elk/logstash/dist/logstash.conf`) tails each file with a per-honeypot `type` and filters (date, geoip, ip_rep, hostname) → Elasticsearch `logstash-*` → Kibana. On a SENSOR, Logstash swaps in `pipelines_sensor.yml` and ships events over HTTPS (`http_output.conf`) through nginx to the hive's `http_input.conf`. A new honeypot needs a Logstash input + filter block to show up in Kibana/Attack Map.
- **Beelzebub and Galah** (`docker/beelzebub/`, `docker/galah/`) build their upstream repos at a pinned commit plus a T-Pot overlay: new Go files in `dist/tpot/` (the flat log format of the former T-Pot forks; Beelzebub also persists the SSH host key and expands `${VAR}` in service YAMLs) and one-line hooks in `dist/tpot.patch`. On an upstream bump, update the commit in the Dockerfile; a hook that no longer applies or compiles fails the build. The log format must stay as it is, ewsposter reads `beelzebub.json` / `galah.json` directly; ES-only normalization (`status_text`, Galah's `http_request.*` / `http_response.*` via `de_dot`) lives in Logstash. Both builders cross-compile on `$BUILDPLATFORM` (Go crashes under QEMU), Galah needs CGO and uses `tonistiigi/xx`.
- **p0f** (`docker/p0f/`) is the original p0f 3.09b C code with T-Pot changes: JSON log (jansson), per-packet skipping of up to two VLAN tags on Ethernet (the original only handled untagged frames), `-o -` for JSON on stdout (offline mode via the entrypoint `dist/run.sh`: no arguments = live capture with a BPF filter for the host's own SYNs by packet direction (`outbound`, live only), arguments go to p0f, own `-j` / `-o` replace the defaults), an optional `conf = <family>[:<share>:<samples>]` field after OS labels in `[tcp:request]` of `p0f.fp`, which p0f writes as `os_family` / `os_confidence` / `os_samples` for client SYNs, and a `ua_family` table in `[http:request]` for the User-Agent signals of `http request` events (`ua_os`, `ua_os_mismatch` against the family of the same connection's SYN, `ua_dishonest`, `http_proxy`); the Kibana objects for it come from a builder script and live in `kibana_export.ndjson`. p0f drops flows after tool (scanner) SYNs on purpose, so those never get HTTP events. The `conf` fields are generated by `docker/p0f/tools/build_os_confidence.py` from public datasets (CC BY 4.0) and must be regenerated after signature changes; scanner signatures stay at the top of `[tcp:request]` (p0f's duplicate check).
- **`tpot` command, the T-Pot Manager** (`tpot` launcher at the repo root, package `tpotctl/`). Names in every text: *T-Pot* is the platform, the *T-Pot Manager* is this tool (command `tpot`), the service is `tpot.service`; `tpotctl/tests/test_look.py` `NamesTest` rejects mixed forms like "Restart tpot". It is the menu + sub-commands for status/`ps`/`images` (the former `dps`/`dpsw`/`dim` aliases now point to them), start/stop/restart, update/restore and the customizer. ### Sensor heartbeat status

`tpotctl/sensors.py` keeps attack `Seen` and `Heartbeat` separate; `observe` is the shared CLI/UI decision:
online only below 180 seconds since HIVE receipt, offline from that threshold, no heartbeat unknown, access
and takeover first. `observations`/`table_rows` drive both six-column tables; `behind` is any known tag mismatch
against the HIVE runtime configuration. `Sensor.version_checked_at` dates the version read by SSH before
deployment/reboot; undated legacy cache values are unverified (the old add path stored the HIVE's version).
Status search paginates the `t-pot_sensor` keyword in batches of 1000, separately from attack aggregation.
API/format errors are displayed; removing access also deletes only the status document and reports partial
failure explicitly. In the UI, `SensorsPane` polls every 30 seconds and repaints ages every two with `sync_rows`,
feeding Status-page counts without another request. Reads are serialized; stale results cannot persist
hostnames or resurrect removed registry entries. Metadata writes occur only after the UI-thread freshness
check. `sensor_heartbeat` smoke exercises the Manager against actual Elasticsearch documents and pagination.
Optional null hostname/IP metadata is removed by ingestion and treated as absent when reading older status
documents; it must not invalidate other sensors' status.

### HIVE fleet update

`tpot sensors update` and the Sensors page share `tpotctl/fleet.py` for
prechecks, canary-first sequencing, heartbeat/runtime verification, failure
decisions and resumable state. The UI polls active runs every 10 seconds;
restarting a prepared retry always asks again about its exact data-loss list,
and `-y` is not that approval. The Sensors page checks saved runs before
asking for sensor sudo credentials, so stopped runs can be discarded without
them; credentials are collected only for prechecks or remote actions that need
them. Fleet state is outside the checkout under
`~/.local/share/tpotce/fleet/`; passwords must stay in memory/private
transport only, never persisted or logged. Mutations of a run are serialized
with a private per-run lock. An interrupted `preparing` run is not resumable,
but can be discarded; `preparing` alone does not mean a remote worker is active.
The 15-minute heartbeat deadline begins when the worker reports completion,
not when its update starts. Keep the CLI and UI resume, discard and retry
semantics aligned.

`python3 -m tpotctl.sensor_dashboard` generates only the `tpot-sensors-*` Kibana objects and updates the
export ZIP; unrelated NDJSON lines stay byte-identical (`--check` validates both). The status data view has
no time field, its `heartbeat.state` runtime field compares ES time with HIVE receipt; timeline and version
series use sensor time, a separate data view for process starts uses `heartbeat.started_at` and distinct
counts. Charts show their top 20 series. This is not a registry view: never-seen/no-access sensors are only
known to the Manager. `sensor_dashboard` smoke compiles the runtime scripts in ES, verifies the aggregations,
imports the saved objects in Kibana and resolves real fields. Regenerate the hash manifest after committing
object changes (the manifest's source is committed history, not the working tree).

## Conventions

- Commit messages use conventional prefixes (`feat:`, `fix:`, `refactor:`).
- Shell scripts use the project's `myVAR` / `fuFUNCTION` naming style in many scripts (e.g. `update.sh`); match the style of the file being edited.
- **Keep `tpot` and the customizer in sync.** They build on other parts of the repo, so a change there is not done until the dependent part is updated and its tests pass:
  - Services and editions (new or changed honeypot, ports, networks, any `compose/*.yml`): the `x-tpot` line in `compose/tpot_services.yml`, catalogue and editions consistent, `python3 -m unittest discover compose/tests`. A removed service also goes into `update.sh` `myDROPPED_SERVICES`. A honeypot that talks to no other container joins `honeypot_local` (ICC off, `test_catalog.py` checks it); one with partner services gets a network of its own (as `nginx_local` for the Elastic Stack and Nginx).
  - Honeypots and the checks: a new or changed honeypot (log format, port, service, how it answers a request, a delayed write) also changes its fixture in `tpotctl/checks/fixtures/` (a real sample event, IPv4, `{src_ip}` / `{src_port}` / `{token}` / `{ts:…}`; `./docker/_tests/run.sh logstash_fixtures`), its entry in the probe table of `tpotctl/checks/probes.py` (`not_tried` / `port_only` with a reason, `LATE_WRITE`; then `python3 -m tpotctl.checks.probes --hptest` for the generated block of `hptest.sh`), `stages.py` where it applies (`ADDRESS_ONLY`, `NO_DEST_PORT`, `SOURCELESS_TYPES`) and, through a PR in the ewsposter repository only, its ewsposter module and the `ews.cfg` section. A change of the Attack Map (Redis channel, map_web, the fields map_data needs) also changes stage 6 of the checks. Open follow-ups are kept in the untracked `OPEN-ITEMS.md` of the main checkout.
  - `.env` keys: change `env.example` and `docker/tpotinit/dist/etc/env.schema.yml` together (same order), and add a case to `docker/tpotinit/tests/env_cases.yml` for a new rule; the tracked `.env` is the config of a new install (`install.sh`) and a byte-identical copy of `env.example` (`cp env.example .env`, `ShippedEnvTest`); `tpotctl/tests/test_envschema.py` fails when they drift, `./docker/_tests/run.sh tpotinit_env` checks the bash side. Give a new key the control that fits (`widget`, `choices`, `show_when`, `llm`, and `unlock` for a fixed one; `tpotctl/tests/test_pickers.py` checks that every choice is valid and every reference exists).
