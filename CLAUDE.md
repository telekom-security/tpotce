# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

T-Pot is a multi-honeypot platform: ~30 honeypots plus NSM tools (Suricata, p0f) and the Elastic Stack, all run as Docker containers via docker compose. There is no application build in the usual sense — the repo is Dockerfiles, compose files, shell scripts, and an Ansible-based installer. The installed checkout lives at `~/tpotce` on the target host, and many scripts hard-code that path (`$HOME/tpotce`).

## Commands

### Building images (`docker/_builder/`)
- `docker/_builder/docker-compose.yml` is the build-only manifest listing every image (multi-arch amd64/arm64 via buildx). Compose reads `docker/_builder/.env`, but the builder exports the values of the run over it: the version is `-t`, else the file `version`, else `TPOT_VERSION` of the environment, else that of `docker/_builder/.env` (never the root `.env`, never `myUI_VERSION`); the repositories and the defaults `TPOT_BUILDER_ARCH` / `TPOT_BUILDER_JOBS` / `TPOT_BUILDER_LIMIT` are an option, else the environment, else the untracked `docker/_builder/.env.local`, else `docker/_builder/.env`, else the built-in default.
- Build: `docker/_builder/builder.sh` (from any folder; Linux only, `fuUI_LINUX_ONLY` exit 3, `-h` everywhere; any user Docker answers to, `docker info` decides, root (`id -u`) only for the upload limit while pushing; another Docker than root's (`fuOTHER_DOCKER`: rootless, Docker Desktop, any context or `DOCKER_HOST` other than the system socket) gets `-l off` / `--set TPOT_BUILDER_LIMIT=off` instead of sudo, and the QEMU hint names rootful Docker only there; a docker-group member whose Docker is down is told to start it). With no option at a terminal it asks (menu: images all / group / pick, options one by one in their order with the default of the settings preselected, a push without root asks "push without a limit / quit" (quit for sudo, not with another Docker than root's: `fuOTHER_DOCKER`), login, summary with the same run as a `-y` command line, which names every value of the environment or the menu and leaves out only what `.env.local` / `.env` / the defaults say (`myFILES_*`), Build / Back; Builder setup; Settings, each question ≤ 76 columns); with `-y`, any option or without a terminal it never asks. Options: `-i a,b` / `-g honeypots,tanner,nsm,elk,tools,all` (union), `-a amd64|arm64|host|both`, `-p` / `--push-hub` / `--push-ghcr` (the existing `docker login`, checked with a 30 s timeout, never asked for: exit 3), `-n`, `-j 1-16`, `-l RATE|off` (tc tbf, only while pushing, only its own limit is removed), `-t` / `--docker-repo` / `--ghcr-repo` (a one-platform push needs its own `-t`, the error names `-a` or the `TPOT_BUILDER_ARCH` it came from), `-T` smoke tests of `docker/_tests/tests` after the build (unless the run builds only this host's platform without pushing, `fuHOST_ONLY`, compose first builds the tested images for this host into docker: no `--load`, compose loads a one-platform build itself; from the cache where the run built this host's platform, after `-n` without it where it did not, e.g. `-a arm64` on amd64, and then the summary warns), `-L`, `--check` / `--setup` / `--uninstall` (buildx builder `mybuilder` + QEMU, always `--builder mybuilder`; buildx keeps builders per user, so `--check` / `--uninstall` say whose builder they handled (`fuWHO`) and name the other one (`fuOTHER_BUILDER`: as a user the sudo hint, as root under sudo the builder in the store of `SUDO_USER` via `getent`); platforms of buildx matched as whole entries, `fuHAS_PLATFORMS`, the same in `--check`, the run and the status line), `--set KEY=VALUE` / `--unset KEY` / `--show-config` (settings in the untracked `docker/_builder/.env.local`, `TPOT_BUILDER_ENV_LOCAL` in tests: `TPOT_DOCKER_REPO`, `TPOT_GHCR_REPO`, `TPOT_BUILDER_ARCH`, `TPOT_BUILDER_JOBS`, `TPOT_BUILDER_LIMIT`; read as text, a UTF-8 BOM ignored; the new text is made in full, then written in place by the shell (`fuWRITE_IN_PLACE`: inode, mode, owner, comments, CRLF and BOM stay), a failed write puts the old text back, a signal waits until the file is whole, exit 3 with a `chown` hint; a key the environment overrides gets a warning; the version is no setting). An option of a build next to `-L`, `--check`, `--setup`, `--uninstall`, `--set` / `--unset` is a usage error (`--show-config` takes them). `-y` is no build option (fine next to `--setup` / `--check` / `-L` / `--set`). The menu keeps the items in their order with the default preselected (`fuUI_CHOOSE --selected`), asks yes / no with `fuUI_CONFIRM --default no`, starts each round anew after Back and prints its command lines with the builder's full path (`mySELF`). For the upload limit, "another Docker" than root's under sudo (rootless, Docker Desktop, any context or `DOCKER_HOST` other than the system socket: `fuOTHER_DOCKER`) gets `-l off` / `--set TPOT_BUILDER_LIMIT=off`, never sudo. A `.env.local` with a NUL byte (UTF-16) is never written (rc 3). A one-platform push (`-a amd64|arm64|host` with `-p` / `--push-*`) needs a `-t` that is no plain version (`^v?[0-9]+(\.[0-9]+)*$`, i.e. `<version>-arm64`), else exit 2; the menu asks again. An `.env.local` that is no text (a NUL byte, UTF-16) stops every run, `--show-config`, `--check` and the menu with exit 3. Exit 0 / 1 image failed / 2 usage or setting / 3 environment / 4 smoke test / 130 cancelled. Compose runs with `-f docker/_builder/docker-compose.yml` plus a generated `log/override.yml` / `override-load.yml` (`platforms: !override`, `tags: !reset []`, needs compose ≥ 2.24.4, checked for `-a`, a push to one registry and the smoke-test build); logs in `docker/_builder/log/` (`TPOT_BUILDER_LOG_DIR`; a run removes the old overrides and empties `builder.log`, the logs of the images it builds, `load.log` when it makes that build and the logs of its tests); under sudo `fuEXIT` (EXIT trap + `fuCANCEL`, once, INT / TERM ignored from its start) removes the limit and chowns the logs back to `SUDO_UID:SUDO_GID` (`chown -R -h` of the resolved path, `fuREAL_PATH`, only when its real parent belongs to that user). The groups (`fuGROUP_IMAGES`) must cover the compose file. builder.sh speaks through `installer/lib/ui.sh` (plain fallback block) and can be sourced for its functions; tests in `tpotctl/tests/test_scripts_builder.py` (stubs for docker incl. `info` / `info --format`, id, uname, chown, tc, ip, getent). `setup_builder.sh` is gone. It is a tool for building releases and on purpose **not** part of the T-Pot Manager: no menu entry, no sub-command, not in the README matrix (`test_scripts.py` `BuilderTest` checks).
- Build one image: `cd docker/_builder && docker compose build <service>`, or `cd docker/<service> && docker compose build` (each service dir has its own standalone `docker-compose.yml` with `build: .`).

### Smoke tests (`docker/_tests/`)
Post-build container tests; they require the image to already exist locally and never build.
- All: `./docker/_tests/run.sh`; list: `./docker/_tests/run.sh --list`
- One: `./docker/_tests/run.sh cowrie` or directly `./docker/_tests/tests/cowrie.sh [--image ...] [--<proto>-port ...]`
- Options: `--timeout SEC`, `--bind-ip IP`, `--keep-artifacts`
- `run.sh`, `lib/common.sh` and every `tests/*.sh` clear CDPATH before their first `cd` (`tpotctl/tests/test_smoke_harness.py`, which also checks every `*.sh` of the checkout that captures `$(cd …)`); a new test starts with `unset CDPATH` before its `SCRIPT_DIR` line.
- Conventions for new tests: one executable `tests/<service>.sh` per honeypot, source `lib/common.sh` (`test_*` helpers for compose, port checks, waiting on log text, cleanup), bind to loopback, prefer dynamic host ports, temp files under `/tmp`, fail with an image build hint when the image is missing. Some tests need host tools (e.g. dicompot needs DCMTK).

### On a running T-Pot host (from `docker/tpotinit/dist/bin/`)
- `hptest.sh [-B file] [--tools-only] [host]` (`tpot check honeypots`) — probes honeypots listed in `~/tpotce/docker-compose.yml` (ports from `docker compose config --format json`, the tools per distribution from `fuTOOLS_FOR`).
- `attackmap_pipeline_test.sh [--types ...] [--ips ...] [--dry-run] [-B file]` (`tpot check pipeline`) — end-to-end check: injected honeypot JSON → Logstash → Elasticsearch → map_data → Redis → map_web WebSocket. Injected events are real and not cleaned up.
- Both run from the *Checks* page in the task screen, in the look of `installer/lib/ui.sh` with `fuMARK` phases (a plain fallback inside the tpotinit image). `mytopips.sh` is `tpot attackers`.

### tpot command and its tests
- `./tpot -h` lists the sub-commands; `./tpot setup` builds the venv.
- `python3 -m unittest discover tpotctl/tests` runs the non-UI tests; the Textual UI tests are skipped there and run with the venv: `~/.local/share/tpotce/venv/bin/python -m unittest discover tpotctl/tests`.
- After changing `tpotctl/requirements.in`: `uv pip compile tpotctl/requirements.in --universal --generate-hashes --python-version 3.9 --only-binary :all: --no-header -o tpotctl/requirements.txt`, then put the header comment back.

### Lifecycle
`install.sh`, `update.sh`, `uninstall.sh`, `restore.sh`, `genuser.sh`, `deploy.sh` (sensor → hive). `install.sh` without `-s` at a terminal installs its packages (+ git, python3-venv), clones the repo to `~/tpotce`, runs `tpot setup` and hands over to the assistant `tpot install` (`tpotctl/installer.py` + `screens/install.py`), which asks everything up front and runs `install.sh -s -M` with the answers (`-P` web password file, `-B` sudo password file, `-c` customizer file; `-M` prints `@@tpot phase|tasks|images|warn` marks the assistant reads with the Ansible `TASK [` lines); without the venv or with `-n` it asks the classic questions (before the playbook). Every mode takes the playbook from the clone. `uninstall.sh -y [-k] [-B file]` (`-k`: `update.sh -y --backup-only --full` first), `tpot uninstall` asks (host name) and execs it. All of them style their output through `installer/lib/ui.sh` (gum, pinned release with sha256, plain text without a terminal or `TPOT_GUM=off`); `install.sh` carries an identical copy of that block because it runs from curl. Besides the messages the block has `fuUI_HELP` (one `-h` layout broken to the terminal by `fuUI_FOLD`, 80 columns without one, rc 0, never the logo), `fuUI_LINUX_ONLY` (update, restore, uninstall, builder stop outside Linux, `uname -s`; WSL2 is Linux), `fuUI_VERSION_GE` (versions as numbers), `fuUI_USAGE_ERROR` (rc 1), `fuUI_RESULT` / `fuUI_SUMMARY` (rc 1 on a fail), `fuUI_CHOOSE_MANY` (gum choose / filter, plain numbers `1,3-5` / `a` / `n`; `--selected <value>` once per value, commas allowed, `\,` for gum), `fuUI_CHOOSE [--selected <value>]` (label and value split at the last colon; the default: gum starts on it, plain text an empty answer takes it), `fuUI_CONFIRM [--default yes|no]` (gum `--default=false`, plain `(Y/n)` / `(y/N)`, answers y / n / yes / no in any case; plain numbers of the choices with spaces only around them), a text of more lines gets `###` before every line, `fuUI_SPIN` (output goes through in the marks mode, `fuUI_MARKS_ON`, and is teed into its log), `fuUI_VERSION` (the one source of the version: `myUI_VERSION`, the file `version` of the checkout, `TPOT_VERSION` of its `.env`) and the T-Pot logo: with `myUI_LOGO=1` `fuUI_BANNER` shows the ANSI logo of the Manager splash with its credits once per chain of scripts (`TPOT_LOGO_SHOWN`), only at a terminal of 80 x 24 or more, never in the marks mode, with `TPOT_GUM=off`, `NO_COLOR` (not empty: the rule for ui.sh, gum by `fuUI_GUM`, say and Rich), `TERM=dumb` or the ascii icons; otherwise the gum wordmark (from `logo.WORDMARK`). `fuUI_LOGO_RENDER` draws it in pure bash in the colours the Manager would take (`fuUI_COLORS`: the one rule of the colours, the same as `prefs.detect_colors`: `TPOT_COLORS`, `tpot.json` (one strict grammar on both sides: an object of plain strings, `fuUI_PREF` / `prefs.read_file`), a `TERM` of dumb / unknown 16, in GNU screen (`STY`) nothing of the terminal outside counts, `COLORTERM`, a true colour `TERM`, outside tmux / screen `TERM_PROGRAM` / `LC_TERMINAL=iTerm2` / `VTE_VERSION` / `KONSOLE_VERSION` / `WT_SESSION`, `*256color` or Apple_Terminal 256, else 16; the cases in `tpotctl/tests/color_cases.json`, `test_colors.py` runs both on them; every gum call goes through `fuUI_GUM`, which hands gum the `COLORTERM` / `TERM` of the rule and with 256 / 16 colours the entries of `theme.PALETTE_256` / `PALETTE_16` (`myUI_GUM_256` / `_16`; the script's own environment stays); tpot.json is read the same in every locale (`fuUI_PREF` in C, UTF-8 checked); `say.py` and the tables of `tpot` (`prefs.console_color_system`) follow the rule too; tables generated from `splash_art.COLOURS`). Its pixels, colour tables and the wordmark are generated between `# >>> tpot logo data >>>` / `# <<< tpot logo data <<<` in both copies by `python3 -m tpotctl.ui_logo`, which also writes the scripts' `# >>> plain fallback` blocks from `ui_logo.FALLBACK` (each block the helpers its script calls; hptest / pipeline of the tpotinit image excluded; `--check` in the tests, `--fallback` prints FALLBACK; run it after changing a script that has a block); `tpotctl/tests/test_ui.py` checks data, colours, sizes, the pty behaviour and the helpers. Both `install.sh` and `update.sh` accept `-b <branch>` / `-r <repo-url>` (env `TPOT_BRANCH` / `TPOT_REPO_URL`) for testing a branch or fork; see README "Testing a Branch" for precedence rules. ### Release
The file `version` at the repo root is the one source of the version number. Scripts and the T-Pot Manager read it (`fuUI_VERSION`; on an installed T-Pot `TPOT_VERSION` of `.env` as fallback) and never carry the number themselves. The places that cannot read it (the `TPOT_VERSION` of `env.example` / `.env` / `docker/_builder/.env`, the image tags of `docker/*/docker-compose.yml`, `CITATION.cff`, the landing page, `genuserwin.ps1`, the smoke test defaults, the p0f examples) are the table `PLACES` in `tpotctl/release.py`: `python3 -m tpotctl.release check` compares them with `version` (exit 1 with the list), `python3 -m tpotctl.release set-version X.Y.Z [--root DIR]` writes `version` and every place (in place: modes and line endings stay; `date-released`, CHANGELOG, README, SECURITY.md stay for you). Places that name a version on purpose (history comments, the honeyaml fork branch, docs, test data, deprecated services) are in `EXCLUDED` with their reason; `tpotctl/tests/test_release.py` fails on a hard coded number that is in neither table, so a new one goes into a table or reads `version`.


### Changing the logo
The T-Pot logo has one source. The pixels and palette of the ANSI template are `PALETTE` / `GRIDS` in `tpotctl/splash_art.py` (between `# >>> splash art data >>>` / `# <<< splash art data <<<`), next to the geometry of its design (`DESIGN`) and its colours per colour system (`COLOURS`: tokens of `theme.py` or `#rrggbb`, exact xterm 256 / VGA entries for 256 / 16); the wordmark is `WORDMARK` in `tpotctl/logo.py`. Everything else is generated, `tpotctl/tests/test_logo_source.py` (`test_no_logo_pixels_elsewhere`) fails on any other tracked file that carries logo data.
1. Template: `t-pot-animate.py` and `80x24/t-pot-animate-80x24.py` in `ansi/` (kept out of git, never committed or copied into the repo).
2. `python3 -m tpotctl.splash_art --import ansi [--import-80x24 FILE] [--check]` parses their `DATA` with `ast.literal_eval` (never runs them), checks 10 colours, the sizes 120x94 / 80x62 / 80x48 and the pixels, and writes `PALETTE` / `GRIDS`; `--check` only compares.
3. Check `DESIGN` against the new picture (`word_x` / `word_y` lettering, `pot_centre` / `pot_radii` pot, `pool_top` / `waves_y` / `pool_y` pool, `drops`, `stars`, `syrup_*`, `magentas`); a new palette also means `COLOURS`.
4. `python3 -m tpotctl.ui_logo` writes pixels, colour tables (`myUI_LOGO_RGB` / `_256` / `_16`) and the wordmark into the data blocks of `installer/lib/ui.sh` and `install.sh` (`--check` in the tests; the block has a budget, `ui_logo.BUDGET`, of 12000 bytes).
5. Tests: `test_logo_source`, `test_look` (splash), `test_ui` (bash rendering), with the venv.
6. The wordmark (`T-Pot`, 21 x 6 pixels) is edited in `tpotctl/logo.py`, then `python3 -m tpotctl.ui_logo` again.

## Architecture

- **`tpotinit` is the orchestrator.** Every compose file starts with the `tpotinit` service (host networking, NET_ADMIN, docker socket, mounts `${TPOT_DATA_PATH}` as `/data`); all other services `depends_on` it being healthy. Its `docker/tpotinit/dist/entrypoint.sh` validates `.env` (rules in `dist/etc/env.schema.yml`, read with `yq` by `dist/bin/env_validate.sh`; all errors at once, service settings only if the service is in the compose file), creates/permissions the data folder, sets up web users, blackhole routes, iptables NFQ rules (for glutton/honeytrap), interface config for the NSM services, imports Kibana objects on fresh HIVE installs, and runs autoheal. The capture interface comes from `dist/bin/capture-if.sh` (`TPOT_CAPTURE_INTERFACE` or the route to the internet); identical copies live in `docker/{suricata,p0f,glutton}/dist/` and must be kept in sync. Host-side helper scripts ship inside this image under `dist/bin/`.
- **Editions are compose files in `compose/`.** `standard.yml`, `sensor.yml`, `mini.yml`, `llm.yml`, `tarpit.yml`, `mobile.yml`, `mac_win.yml`. The root `docker-compose.yml` is the active one and is a copy of `compose/standard.yml` — keep them in sync when editing the standard edition. `tpot_services.yml` is the service catalogue that `compose/customizer.py` (logic in `customizer_core.py`, UI-free `State` + text dialog in `customizer_tui.py`, full screen dialog in `tpotctl/screens/customizer.py`; headless/`--rebuild` need only stdlib + PyYAML, Python ≥ 3.9, the distro package comes from the installer / `update.sh` `fuCUSTOMIZER_DEPS`, else the tpot venv) uses to build a custom compose file: an edition as base plus added/removed services and host-port overrides, written into a `# customizer:` header with a sha256 of the body so `update.sh` (`fuRESTORE_CUSTOM`) can `--rebuild` it on updates unless it was hand-edited. Every catalogue service needs an `x-tpot` line (group, description, optional requires/conflicts/hidden/hive_only/linux_only/required); editions may only differ from the catalogue in ports, networks and depends_on (mac_win also network_mode, cap_add, volumes). Run `python3 -m unittest discover compose/tests` after touching any compose file. Adding/changing a service usually means touching several of these files plus `docker/_builder/docker-compose.yml` and `docker/<service>/docker-compose.yml`.
- **Configuration**: `.env` (defaults in `env.example`) feeds both compose variable substitution (`TPOT_REPO`, `TPOT_VERSION`, `TPOT_PULL_POLICY`, `TPOT_DATA_PATH`, ...) and tpotinit (`TPOT_TYPE=HIVE|SENSOR`, `TPOT_BLACKHOLE`, `TPOT_HIVE_*`, `WEB_USER`, ...). Note `.env` and `docker-compose.yml` are listed in `.gitignore` but are tracked — edits to them do show in diffs.
- **Per-service layout**: `docker/<service>/{Dockerfile, docker-compose.yml, dist/}`. Containers are generally `read_only` with tmpfs, run as uid/gid 2000, and write logs to `${TPOT_DATA_PATH}/<service>/log`. Image tags follow the file `version` (see *Release*).
- **Data flow**: honeypots write JSON/log files under `/data/<service>/log/` → Logstash (`docker/elk/logstash/dist/logstash.conf`) tails each file with a per-honeypot `type` and filters (date, geoip, ip_rep, hostname) → Elasticsearch `logstash-*` → Kibana. On a SENSOR, Logstash swaps in `pipelines_sensor.yml` and ships events over HTTPS (`http_output.conf`) through nginx to the hive's `http_input.conf`. A new honeypot needs a Logstash input + filter block to show up in Kibana/Attack Map.
- **Beelzebub and Galah** (`docker/beelzebub/`, `docker/galah/`) build their upstream repos at a pinned commit plus a T-Pot overlay: new Go files in `dist/tpot/` (the flat log format of the former T-Pot forks; Beelzebub also persists the SSH host key and expands `${VAR}` in service YAMLs) and one-line hooks in `dist/tpot.patch`. On an upstream bump, update the commit in the Dockerfile; a hook that no longer applies or compiles fails the build. The log format must stay as it is, ewsposter reads `beelzebub.json` / `galah.json` directly; ES-only normalization (`status_text`, Galah's `http_request.*` / `http_response.*` via `de_dot`) lives in Logstash. Both builders cross-compile on `$BUILDPLATFORM` (Go crashes under QEMU), Galah needs CGO and uses `tonistiigi/xx`.
- **p0f** (`docker/p0f/`) is the original p0f 3.09b C code with T-Pot changes: JSON log (jansson), per-packet skipping of up to two VLAN tags on Ethernet (the original only handled untagged frames), `-o -` for JSON on stdout (offline mode via the entrypoint `dist/run.sh`: no arguments = live capture with a BPF filter for the host's own SYNs by packet direction (`outbound`, live only), arguments go to p0f, own `-j` / `-o` replace the defaults), an optional `conf = <family>[:<share>:<samples>]` field after OS labels in `[tcp:request]` of `p0f.fp`, which p0f writes as `os_family` / `os_confidence` / `os_samples` for client SYNs, and a `ua_family` table in `[http:request]` for the User-Agent signals of `http request` events (`ua_os`, `ua_os_mismatch` against the family of the same connection's SYN, `ua_dishonest`, `http_proxy`); the Kibana objects for it come from a builder script and live in `kibana_export.ndjson`. p0f drops flows after tool (scanner) SYNs on purpose, so those never get HTTP events. The `conf` fields are generated by `docker/p0f/tools/build_os_confidence.py` from public datasets (CC BY 4.0) and must be regenerated after signature changes; scanner signatures stay at the top of `[tcp:request]` (p0f's duplicate check).
- **`tpot` command, the T-Pot Manager** (`tpot` launcher at the repo root, package `tpotctl/`). Names in every text: *T-Pot* is the platform, the *T-Pot Manager* is this tool (command `tpot`), the service is `tpot.service`; `tpotctl/tests/test_look.py` `NamesTest` rejects mixed forms like "Restart tpot". It is the menu + sub-commands for status/`ps`/`images` (the former `dps`/`dpsw`/`dim` aliases now point to them), start/stop/restart, update/restore and the customizer. It is a thin layer: `update.sh`, `restore.sh`, `install.sh`, `uninstall.sh` and `installer/install/deploy.yml` stay the engine and are called, not reimplemented; `update`/`restore`/`customize` hand all options through unchanged. `tpotctl/ops.py` and `cli.py` hold the logic, `app.py` + `screens/` + `widgets/` the Textual UI. The look comes from the T-Pot logo (`doc/t-pot_wallpaper_*.png`): `theme.py` has the colour tokens (magenta `#E20074`, petrol, glass, mist, key, ash, comb, wax) and the one theme `tpot` (no theme switching, on purpose), `glyphs.py` the icon sets `unicode` (default, one cell wide each, tests check it) / `nerd` / `ascii`, `logo.py` the wordmark (`T-Pot`, capital T and P, 21 x 6 pixels) as a pixel map, `splash_art.py` the pixels and palette of the T-Pot ANSI logo (imported from the template in `ansi/`, kept out of git, with `--import`: 120 / 80 / 80 x 24 variants, 10 colours, half blocks), the geometry of its design `DESIGN` and its colours `COLOURS` (see *Changing the logo*), `splash_anim.py` the eight second splash from them as pure frames (`Splash.frame(t)`: the parts assemble, the template's 6 s cycle, the credits type with an afterglow, it crumbles; `variant_for` picks 120 x 49 / 80 x 33 / 80 x 24, none below; its colours are the theme tokens in true colour and palette entries with 256 / 16, `colours()`; `screens/splash.py` only plays them, `TPOT_SPLASH=off`), `prefs.py` the icon set and the colours in `~/.config/tpotce/tpot.json` (for `auto` `prefs.detect_colors(environ)`, the rule of `fuUI_COLORS`, which `apply_color_system` hands to Textual for auto too, on Windows only truecolor; `TPOT_ICONS` / `TPOT_COLORS` win; the launcher and `compose/customizer.py` hand the colours to Textual as `TEXTUAL_COLOR_SYSTEM` before it is imported, `prefs.apply_color_system`, marked with `TPOT_COLORS_SET` so a restart of the Manager takes a new choice and only a value of the user's own wins). `theme.build(system)` makes `STYLE` / `TPOT_THEME` from the true colours, from `PALETTE_256` (exact xterm 256 entries) for a terminal that only says 256 colours (SSH without `COLORTERM`, tmux) or from `PALETTE_16` (the ANSI colours, `TERM=xterm` / `screen`; `TPOT_COLORS=16` is Textual's `standard`), `theme.color_system()` mirrors `textual.constants.COLOR_SYSTEM` (Rich's detection for auto), so palette and output never disagree; alpha blends that turn red there go through theme variables (`$focus-tint`, `$modal-dim` for dialogs and ctrl+p, `block-cursor-blurred-background`), `test_look.py` `ColoursTest` renders the app in 256 and 16 colour mode and checks every colour Textual derives (`generate()`) for maroon. Rich texts take colours from `theme.color()` and glyphs from `glyphs.g()`, never hard-coded, so `f2` can repaint them. The Status page is fed by `ops.containers()` (honeycomb in `widgets/comb.py`, states from `ops.cell_state()`), `system.py` (/proc) and `events.py` (attacks per minute from Elasticsearch, Suricata / P0f left out); `commands.py` is the `ctrl+p` palette (pages, actions, every setting). `editions.py` switches the edition (`tpot edition set`, *Edition & services*): stop, keep the compose file in `~/tpot_backups`, copy `compose/<edition>.yml`, `TPOT_TYPE=HIVE` for a SENSOR that becomes a HIVE, prune the networks, start; its texts are `installer.EDITIONS`. Scripts and `tpot` commands that the menu runs go through the task screen (`screens/task.py`: `@@tpot` marks of `fuMARK`, read by `runlog.py`; `changed checkout` offers Restart the Manager after a failure too, `fail <phase>` turns that phase red; the child run by `engine.py`, a sudo password as a 0600 file for `-B` / `--become-file`); Ctrl+C at a question of `tpot` ends it with `Cancelled.` and exit code 130 (`bootstrap.cancelled`), every foreground child goes through `bootstrap.run_child` / `cli.call` (on `bootstrap.wait_child`: 128 + signal, a ^C the child survives but fails on is a cancel too), `bootstrap.sigint_to` makes a ^C only count where the work must finish (the Runner of the menu, which also keeps Textual's asyncio SIGINT handler from ending the app, `sensors add` from the grant on, the edition switch), 2 means it cannot ask (no terminal: `--yes` / `--password-stdin`), an interrupted `sensors add` takes the access back; the messages of `tpot` and the customizer come from `say.py`, the same text as `installer/lib/ui.sh`. Keys: the arrows move through every page and dialog the same way (`widgets/nav.py`: up / down by line, the widgets under one horizontal container are one line, lists, tables, text fields and scrollers first to their edge through `NavInput` / `NavDataTable` / `NavOptionList` / `NavScroll` / `NavRichLog`; left / right within a line and between tabs; left at the start of a line on a page back to the menu, never from a text field; enter on a list whose buttons act on the choice (`enter_goes_on`: backups; the editions say so for the one in use) takes it and goes on to them, enter on a web user or sensor offers the actions of that row (`offer_row_actions`)). The apps take `nav.BINDINGS` + `ArrowNav`, every dialog derives from `NavModal` (a modal screen does not see the App bindings); `tpotctl/tests/test_nav.py` walks every page, screen and app and fails on a widget the arrows cannot reach. `TpotSelect` drops its own up / down bindings for it, esc goes back to the menu, right / enter into a page, `ctrl+s` saves the Settings / LLM page (`SettingsPane.action_save`, in the footer there). Settings fields are built from the schema (`widgets/fields.py`): `widget` switch / choice / interface / timezone / llm_model / llm_url, `choices` + `custom`, `show_when`, `llm`, `offer` (shown for every edition, problems only warn where the service is absent: the LLM keys), `unlock` (the warning before a fixed system key can be changed: Unlock button, `tpot env set --unlock`, `Settings.change(unlocked=...)`; the keys of `settings.MANAGED_BY` never unlock; `Settings.fixes()` is the exception: a `TPOT_OSTYPE` that does not fit the host of `ops.host_ostype()` (the Docker kernel, like tpotinit; `TPOT_HOST_OSTYPE` wins, the tests set it) is an error, and the value that fits is written without an unlock and proposed on the Settings page); tpotinit ignores these keys. The pickers (`screens/pickers.py`) use `netinfo.py` (same detection as `capture-if.sh`, keep both in sync), `tz.py` and `llm.py` (Ollama `/api/tags`, OpenAI `/v1/models`; `discover` / `scan` for an Ollama on 11434, a loopback hit is not offered because the honeypots run in Docker; `test` sends one prompt). The *LLM* page (`LlmPane`) is a `SettingsPane` with its own prefix (`#llm-*`), the LLM keys grouped by honeypot; `tpot llm` is its command. It runs from a venv in `~/.local/share/tpotce/venv` (`tpotctl/bootstrap.py`, standard library only) built from `tpotctl/requirements.txt`: pinned with hashes, wheels only (`pip --require-hashes --only-binary :all:`). The installer links `/usr/local/bin/tpot` and runs `tpot setup` (`install.sh` and the assistant say at the end whether `tpot` is a command), `update.sh` `fuTPOT_SETUP` refreshes it (a file of your own there only warns), uninstall removes link and venv. Started as `./tpot` from `~/tpotce` without the link, the launcher offers it once (`bootstrap.ensure_link`, `sudo ln -sfn`, note in `~/.local/share/tpotce/link-asked`); a Python without venv module on apt systems gets the offer to install `python3-venv` / `python3.X-venv` (`bootstrap.offer_venv_package`, only at a terminal). `tpot` refuses root and only uses `sudo` for `systemctl` (and hands a sudo password as a file to the scripts it runs). Every page of `PANES` says where it works (4th field: `any`, `host`, `hive`, `host+hive`); elsewhere it stays in the menu as a `LockedPane` (why, what instead), its own class is not built there, so nothing calls docker, systemctl or Elasticsearch on macOS / Windows or on a SENSOR. The README matrix of *The T-Pot Manager (tpot)* names every sub-command with its page and where it works (`test_app.py` checks it). `tpot env list|get|set|check` and the Settings page check against the same `env.schema.yml` as tpotinit (Python in `tpotctl/envschema.py`, writer that keeps both `KEY=value` / `KEY: "value"` forms, comments, owner and mode in `tpotctl/envfile.py`, logic in `tpotctl/settings.py`); they never write a value tpotinit would reject or replace. Both implementations must pass the shared cases in `docker/tpotinit/tests/env_cases.yml` (Python: `tpotctl/tests/test_envschema.py`, bash: `./docker/_tests/run.sh tpotinit_env`). `tpot users list|add|passwd|remove` and the Web users page (`tpotctl/users.py`) manage `WEB_USER`: new and changed passwords are bcrypt via `htpasswd -n -i -B` (password on stdin, never in argv; tpotinit image as fallback), cracklib or 12 characters with confirmation for weak ones, entries T-Pot rejects are marked and repaired by `passwd`, the last working user cannot be removed. They rewrite `data/nginx/conf/nginxpasswd` **in place** (it is bind mounted on its own, a rename would not reach nginx), nginx reads it per request, so no restart. `genuser.sh` is a wrapper on `tpot users add` with the tpotinit container as fallback (like `deploy.sh` for `tpot sensors add` it checks the options of that command itself before anything is shown, a wrong one is exit 1). `tpot sensors list|add|remove|set|cert` and the Sensors page (`tpotctl/sensors.py`, HIVE only): access is `LS_WEB_USER` (bcrypt, `lswebpasswd` rewritten in place like `nginxpasswd`), the registry `data/sensors.json` holds only metadata and is rebuilt from `LS_WEB_USER` when missing (migration of earlier releases); `add` checks SSH (port 64295 or `--ssh-port`), the hive certificate SANs (renews it with the same openssl parameters as tpotinit if the hive address is missing), grants access first, runs the unchanged `installer/install/deploy.yml` and takes the access back if it fails, then shows the password once; `cert --distribute` runs `installer/install/sensor_cert.yml`. nginx `lsweb.conf` passes the authenticated user as `X-TPot-Sensor`, Logstash `http_input.conf` turns `[headers][x_tpot_sensor]` into `t-pot_sensor`, which `tpot sensors list` aggregates in Elasticsearch (127.0.0.1:64298) for "last seen". `deploy.sh` is a wrapper on `tpot sensors add` with the old steps as fallback; both take a SENSOR by IPv4, IPv6 or name (an ssh alias with `_` too) and the HIVE by IPv4 or a name with an A record only (`check_hive_address`: what tpotinit takes as `TPOT_HIVE_IP`, the Logstash URL has no brackets for IPv6 and the containers of a SENSOR have no IPv6, so an IPv6-only HIVE cannot take sensors yet), user names as `check_user` (capitals allowed; `re.fullmatch`, no trailing newline).
- **Attack Map** (`docker/elk/map/`): builds from the external `telekom-security/t-pot-attack-map` repo at a pinned tag; `map_data` polls ES and publishes to Redis, `map_web` serves the WebSocket/UI behind nginx.
- **nginx** (`docker/nginx/`) is the single web entry point (port 64297) proxying Kibana, CyberChef, Elasticvue, Attack Map, and the sensor ingest endpoint.
- **Installer**: `install.sh` bootstraps prerequisites and runs the Ansible playbook `installer/install/tpot.yml` (supports multiple distros); `installer/remove/` mirrors it for uninstall; the sshd drop-in `/etc/ssh/sshd_config.d/tpot.conf` (checked with `sshd -t`) accepts `COLORTERM LC_TERMINAL LC_TERMINAL_VERSION` (`update.sh` `fuSSHD_DROPIN` brings the old one-line drop-in of an earlier T-Pot along, only that exact file, checked with `sshd -t`, put back if the check fails; through sudo where the folder is 0700 root (AlmaLinux, Fedora, RHEL, Rocky), a summary warning if even sudo cannot look); `install.sh` hands the web password to htpasswd on stdin only, it is never exported; every failure of `install.sh` ends with `@@tpot fail <phase>` and `@@tpot phase failed` (the assistant names the log of that step, or the output where a step writes none).

## Conventions

- Commit messages use conventional prefixes (`feat:`, `fix:`, `refactor:`).
- Shell scripts use the project's `myVAR` / `fuFUNCTION` naming style in many scripts (e.g. `update.sh`); match the style of the file being edited.
- **Keep `tpot` and the customizer in sync.** They build on other parts of the repo, so a change there is not done until the dependent part is updated and its tests pass:
  - Services and editions (new or changed honeypot, ports, networks, any `compose/*.yml`): the `x-tpot` line in `compose/tpot_services.yml`, catalogue and editions consistent, `python3 -m unittest discover compose/tests`. A removed service also goes into `update.sh` `myDROPPED_SERVICES`. A honeypot that talks to no other container joins `honeypot_local` (ICC off, `test_catalog.py` checks it); one with partner services gets a network of its own like `tanner_local`.
  - `.env` keys: change `env.example` and `docker/tpotinit/dist/etc/env.schema.yml` together (same order), and add a case to `docker/tpotinit/tests/env_cases.yml` for a new rule; `tpotctl/tests/test_envschema.py` fails when they drift, `./docker/_tests/run.sh tpotinit_env` checks the bash side. A new rule type needs both `env_validate.sh` and `envschema.py`. Give a new key the control that fits (`widget`, `choices`, `show_when`, `llm`, and `unlock` for a fixed one; `tpotctl/tests/test_pickers.py` checks that every choice is valid and every reference exists). A change to `capture-if.sh` goes into `tpotctl/netinfo.py` too.
  - Installer: the distribution table of `install.sh` (`mySUPPORTED_*`) and `tpotctl/installer.py` (`SUPPORTED`), the editions (`myEDITION` cases ↔ `EDITIONS`), the `@@tpot` marks ↔ `installer.Progress`, the ui block of `install.sh` ↔ `installer/lib/ui.sh` (`tpotctl/tests/test_installer.py` checks all four). A new gum release: new version and both sha256 from its signed `checksums.txt`, in both copies.
  - A new menu page needs an icon in every set of `tpotctl/glyphs.py` (`pane_<key>`, `test_look.py` checks it) and a `REPAINT` entry in `app.py`.
  - Options or prompts of `update.sh` / `restore.sh`: `tpot update|restore` pass them on unchanged, but the help and menu texts in `tpotctl/cli.py` / `tpotctl/app.py` must still match. The menu runs both in the task screen (`-B`, `restore.sh -g` with the groups of `ops.GROUP_TEXT`, whose questions `test_scripts.py` keeps the same as in `restore.sh`); their output goes through `fuUI_*` and their phases through `fuMARK` (a plain fallback block for a checkout without `installer/lib/ui.sh`), no raw `echo "###"` (tests check it). The same holds for every script a person runs: source `installer/lib/ui.sh`.
  - A script a person runs: `unset CDPATH` before its first `cd` (an exported CDPATH makes `$(cd "$(dirname "$0")" && pwd)` print two lines; `test_scripts_look.py` `CdpathTest`), `myUI_LOGO=1` before its first `fuUI_BANNER` if it asks anything, `fuUI_HELP` for `-h` (exit 0), `fuUI_USAGE_ERROR` for a wrong option (exit 1, the builder 2), `fuUI_SPIN` for long steps, a `fuUI_SUMMARY` at the end, its plain fallback block defining every helper it calls (`python3 -m tpotctl.ui_logo --fallback`), no `read -p` of its own and no version literal (`tpotctl/tests/test_scripts_look.py`, `test_ui.py`, `test_release.py`).
  - Web users (`WEB_USER`, its format, `nginxpasswd`, the nginx auth config, `genuser.sh`, the web user part of `install.sh`): change `tpotctl/users.py` and `tpotctl/tests/test_users.py` with them. Sensors (`LS_WEB_USER`, `TPOT_HIVE_USER`, `deploy.yml`, `sensor_cert.yml`, `http_output.conf`, `http_input.conf`, the nginx ingest config `lsweb.conf`, the certificate creation in tpotinit): change `tpotctl/sensors.py` and `tpotctl/tests/test_sensors.py` with them.
  - Python dependencies only through `tpotctl/requirements.in` / `requirements.txt` (hashes, wheels only), nothing installed outside the venv besides the distro PyYAML.
  - A new admin task becomes a `tpot` sub-command and/or menu entry, not another standalone script. Every menu pane needs a sub-command (`tpotctl/tests/test_app.py` checks it).
  - Run both `compose/tests` and `tpotctl/tests` (the latter also with the venv for the UI tests).
- CI (`.github/workflows/`) only runs a README link checker and issue housekeeping — there is no automated build or test in CI, so run the relevant smoke test locally.
